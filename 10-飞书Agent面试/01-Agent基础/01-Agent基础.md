# 01-Agent 基础

## 01 Agent、LLM 和 Workflow 有什么区别？

### 面试官追问

**面试官：** 你理解的 AI Agent 是什么？它和直接调用大模型有什么区别？又和 Workflow 有什么区别？

**我：** Agent 就是更强的大模型，可以调用工具。Workflow 就是一串固定流程。

**面试官：** 大模型输出一次工具调用，就自动变成 Agent 了吗？如果一个固定审批流程里面使用了大模型，它也是 Agent 吗？这几个概念里，到底是谁决定下一步做什么？

这道题真正考察的，不是你能不能背出三个定义，而是你能不能说清楚：决策权在哪里，流程能不能根据运行结果动态变化。

### 常见错误回答

“LLM 是模型，Agent 是带工具的 LLM，Workflow 是固定流程。”

这句话方向没错，但太浅了。它没有回答工具是谁执行的、结果回来之后谁决定下一步、失败后怎么办，以及系统如何知道什么时候应该停止。

### 30 秒简答

LLM 是负责理解和生成的概率模型，它可以根据上下文输出文本，也可以输出结构化的动作意图，但它本身没有权限读取文件、调用接口或修改数据。

Agent 是围绕 LLM 搭建的一套执行系统。它给模型提供目标、工具、状态和控制循环，让模型能够根据观察结果决定下一步，调用工具，继续观察，直到完成任务或触发停止条件。

Workflow 是预先定义好的编排流程，步骤和分支主要由代码或规则决定。里面可以使用 LLM，但整体路线不交给模型自由决定。

简单说：流程稳定、必须审计时优先 Workflow；下一步取决于实时信息时才引入 Agent；生产系统通常是 Workflow 管边界，Agent 处理不确定的局部任务。


### 原理拆解

#### 1. LLM 是推理引擎，不是完整应用

大模型可以完成摘要、分类、问答和结构化输出。例如，它可以返回：

```json
{"action": "search_document", "arguments": {"query": "本周项目风险"}}
```

但这只是一个动作意图。真正的搜索、权限判断、参数校验和结果回传，都需要宿主程序完成。

#### 2. Agent 是一个带控制循环的系统

Agent 的基本链路可以表示为：

```text
目标与指令
-> LLM 判断下一步
-> 运行时校验并执行工具
-> 观察工具结果
-> 更新状态
-> 继续执行或返回结果
```

它和普通 LLM 调用最大的区别，是允许系统根据中间结果改变路线。例如搜索没有结果时改写查询，接口超时时选择重试，证据不足时向用户追问。

#### 3. Workflow 是确定性编排

例如一个报销流程：

```text
接收申请 -> 校验字段 -> 查询预算 -> 风险判断 -> 人工审批 -> 通知结果
```

这里可以让 LLM 负责识别申请内容或生成通知文本，但是否需要审批、预算是否超限、谁有审批权限，应该由代码和业务规则控制。

#### 4. 三者对比

| 维度 | LLM | Agent | Workflow |
| --- | --- | --- | --- |
| 主要职责 | 理解、生成、判断 | 围绕目标动态行动 | 执行确定流程 |
| 下一步由谁决定 | 宿主程序 | 模型和运行时共同决定 | 代码或规则决定 |
| 工具调用 | 可有可无 | 核心能力 | 可作为某个流程节点 |
| 状态 | 当前请求上下文 | 任务状态和记忆 | 流程状态 |
| 适用场景 | 单轮生成 | 不确定、多步骤任务 | 稳定、可审计流程 |

### 企业协作场景

用户在企业 IM 里说：“帮我整理本周销售风险，参考项目文档、群聊和数据表，最后生成一份管理层简报。”

- 直接调用 LLM，只能处理已经放进上下文的文字。
- Agent 可以自主搜索授权文档、读取数据表、发现信息缺失并继续查询，最后生成带来源的简报。
- 如果这个简报每周五固定生成，数据源和格式都固定，那么用 Workflow 更稳定。

比较成熟的方案是混合架构：Workflow 负责定时触发、权限和最终发送，Agent 负责不确定的信息检索与内容综合。

### 工程方案与取舍

1. 默认先用 Workflow。它更容易测试、审计、回放和恢复。
2. 只有当所有路径无法提前枚举时，才加入 Agent 的动态决策。
3. 高风险动作不能只靠 Prompt 约束，必须在模型外部做权限、参数、额度和确认校验。
4. 不要让模型直接执行“万能工具”，应拆成范围明确、权限明确的小工具。

Agent 增加的是灵活性，同时也会增加延迟、成本和非确定性。面试时能主动说出这部分代价，通常比只说“Agent 更智能”更有说服力。

#### 5. 一个实用的选型判断框架

面试中如果被问“到底该不该做 Agent”，可以从四个问题开始判断：

1. **任务目标是否清晰？** 如果输入、步骤和输出都比较固定，优先考虑 Workflow；如果用户只给了一个目标，具体路径要根据搜索结果决定，才有 Agent 的空间。
2. **下一步是否依赖实时观察？** 如果每一步都能提前写死，就不需要模型动态规划；如果必须看完上一步结果才能决定下一步，Agent 的循环才有价值。
3. **动作风险是否可控？** 只读检索、摘要和草稿生成风险较低，可以允许更大的动态性；发送消息、修改数据、审批和删除操作必须收紧权限，并加入确认节点。
4. **失败后能否恢复？** 如果任务没有清晰的超时、重试、回滚和人工接管机制，即使模型能完成 Demo，也不适合直接做成 Agent。

可以把选型简单理解成一条光谱：左侧是固定编排，右侧是开放式自主执行。实际系统不需要把自己归类成纯 Workflow 或纯 Agent，而是把稳定部分固化，把不确定部分交给模型。

#### 6. 生产系统的最小闭环

以企业内部的“查资料并创建任务”为例，一个可落地的最小闭环通常包括：

```text
接收用户目标
-> 识别意图和操作风险
-> 确定允许访问的数据源
-> Agent 规划检索步骤
-> 工具层执行受限查询
-> 生成带来源的草稿
-> 用户确认写操作
-> Workflow 完成任务创建和通知
```

这里 Agent 只负责处理“去哪里找、哪些信息相关、如何组织草稿”等不确定问题。任务创建和通知仍然由确定性的服务接口完成，接口会再次校验用户身份、字段完整性和幂等键。

如果某个工具失败，系统应该把失败分成几类：参数错误通常需要重新生成参数，权限错误需要提示用户，临时网络错误可以有限重试，业务规则拒绝则不能让模型绕过。不同失败类型要对应不同处理路径，而不是统一告诉模型“请再试一次”。

#### 7. 如何证明 Agent 选型是有效的

不能只用“回答看起来不错”评价 Agent。至少应该建立一组真实任务样本，记录以下指标：任务完成率、关键工具调用准确率、平均调用轮数、P95 延迟、单任务 Token 成本、需要人工接管的比例，以及高风险动作拦截率。

还要和 Workflow 或普通 LLM 版本做对照。如果 Agent 只让完成率提高了 2%，却让延迟增加一倍、成本增加三倍，就不一定值得采用。反过来，如果它能覆盖大量无法预先枚举的检索路径，同时关键写操作仍由规则控制，这才是合理的收益。

面试时可以补一句：我会先从只读任务开始灰度，收集 Trace 和失败样本，再逐步开放低风险写操作，最后才考虑高风险动作。这样既能验证动态决策的价值，也能控制上线风险。

### 继续追问

**Q：只调用一次工具的聊天机器人算 Agent 吗？**  
不一定。一次结构化工具调用可以只是工具增强的 LLM 交互。只有当系统具备目标驱动、持续观察、动态路由和受控终止等特征时，才更接近 Agent。

**Q：Agent 能不能替代 Workflow？**  
通常不能。支付、审批、删除数据、合规检查等流程不能把关键控制权交给概率模型。

**Q：Agent 设计最容易犯什么错？**  
把本来可以用确定性规则解决的问题，交给模型自由发挥。

### 面试总结

回答时先把控制边界说清楚：LLM 负责理解和生成，Agent 负责围绕目标执行动态循环，Workflow 负责确定性编排。选型原则是：稳定流程用 Workflow，不确定任务才用 Agent，生产系统通常把两者组合起来。

## 02 Agent 的核心组件与 Agent Loop

### 面试官追问

**面试官：** Agent 架构里有哪些核心组件？

**我：** 有模型、Prompt、工具和记忆。

**面试官：** 这是组件清单，不是架构。工具定义从哪里来？谁真正执行工具？工具超时怎么办？哪些状态会回到上下文？系统怎么知道任务完成了？

这道题不能只罗列名词，要把一次请求从进入系统到返回结果的执行链路讲出来。

### 常见错误回答

“大模型选择工具，工具返回结果，大模型再生成答案。”

这句话省略了权限、参数校验、状态管理、失败处理、循环上限和可观测性。Demo 能跑，不代表系统可以上线。

### 30 秒简答

我会把 Agent 分成六层：目标与指令、LLM 推理、工具注册、执行运行时、状态与记忆、治理与可观测性。

Agent Loop 的过程是：接收目标和当前状态，由 LLM 决定返回答案、调用工具还是继续追问；运行时在模型外部校验并执行动作；工具结果写回状态；系统再判断是否继续、重试、升级人工或结束。

其中最重要的边界是：模型只负责提出动作意图，真正的执行必须由受控运行时完成。


### 原理拆解

#### 1. 目标与指令

这一层定义任务目标、输出格式、允许使用的工具、禁止行为和停止条件。Prompt 可以告诉模型应该怎么做，但不能代替代码中的安全校验。

#### 2. LLM 推理层

模型接收目标、相关上下文、工具 Schema 和最新观察结果，输出两种结果之一：

- 最终回答；
- 结构化动作请求，例如工具名称和参数。

#### 3. 工具注册层

工具不只是一个函数名，还应该描述：参数结构、必填字段、权限要求、超时、重试方式、是否幂等和输出大小限制。

#### 4. 执行运行时

```text
模型提出动作
-> 校验工具和参数
-> 检查用户权限与风险等级
-> 执行工具
-> 规范化并裁剪结果
-> 把观察结果写回状态
```

运行时还要处理超时、限流、网络错误、重复执行和工具返回格式异常等问题。

#### 5. 状态与记忆

当前任务状态应该保存计划、已完成步骤、工具结果、重试次数和待处理问题。长期记忆则只保存经过筛选、授权和确认的持久信息。

不要把所有历史对话都塞进 Prompt。上下文越长不代表决策越好，过多的旧信息反而可能让模型忽略当前目标。

#### 6. 治理与可观测性

一次完整 Trace 至少要能看到：用户请求、模型选择的工具、实际执行参数、权限结果、工具耗时、返回结果、重试原因、Token 消耗和最终输出。

没有 Trace，Agent 出错时就只能重新猜；没有评测集，也无法判断改 Prompt 后到底有没有变好。

### Agent Loop

```text
用户目标
-> 构建当前上下文
-> LLM 判断：回答 / 调工具 / 追问
-> 运行时校验并执行
-> 更新任务状态
-> 检查完成条件、预算和风险
-> 继续循环或返回结果
```

循环必须有明确上限，例如最大轮数、最大工具次数、最大 Token 预算和截止时间。否则模型可能重复调用同一个工具，或者在证据不足时无限尝试。

### 企业协作场景

用户说：“帮我找到最新的入职政策，总结三项变化，并为团队创建任务。”

一个合理的 Agent 应该：

1. 识别用户身份，并确认他能访问哪些文档。
2. 搜索政策文档并判断版本是否最新。
3. 生成带来源的变化摘要。
4. 先展示拟创建的任务，等待用户确认。
5. 确认后再创建任务，并返回执行结果。

搜索文档、创建任务和发送通知应该是不同工具，不能合并成一个没有边界的“帮我完成所有事情”工具。

### 工程方案与取舍

| 设计选择 | 好处 | 代价 |
| --- | --- | --- |
| 工具描述更详细 | 选择准确率更高 | 占用更多上下文 |
| 暴露更多工具 | 能力范围更大 | 选择歧义和治理成本更高 |
| 工具返回完整日志 | 信息更全 | 上下文膨胀、干扰判断 |
| 保留更长记忆 | 连续性更好 | 成本、隐私和过期信息增加 |
| 增加重试次数 | 临时失败恢复更好 | 延迟和重复副作用增加 |

第一版系统建议采用少量窄工具、严格参数校验、有限循环、完整 Trace。先把运行边界做稳，再增加规划和长期记忆。

#### 6. Loop 中的状态应该怎么设计

不要只保存一串自然语言对话。一个可恢复的任务状态至少可以包含：

```json
{
  "task_id": "risk-report-001",
  "goal": "整理本周项目风险",
  "plan": [{"id": "search_docs", "status": "done"}],
  "observations": [{"source_id": "doc-123", "content_ref": "artifact-9"}],
  "pending_actions": [],
  "retry_count": 1,
  "budget": {"max_steps": 8, "used_steps": 3},
  "approval": {"required": true, "status": "pending"}
}
```

模型可以读取其中经过筛选的内容，但不能直接修改所有字段。比如 `approval.status`、权限结果和任务完成状态，应由运行时或业务服务写入。这样即使模型输出了错误的“已完成”，系统也不会把任务误判为成功。

#### 7. 工具执行不是简单的函数调用

工程上需要给工具加上统一的执行协议：输入 Schema、身份信息、超时、幂等键、错误码和输出 Schema。对查询工具，可以允许有限重试；对创建任务或发送消息这类有副作用的工具，必须防止重复执行。

例如 Agent 第一次创建任务后网络超时，模型可能以为没有成功而再次创建。运行时应该使用业务幂等键查询原操作结果，而不是盲目重发。对无法回滚的操作，可以先生成待确认草稿，再由用户确认后执行。

工具返回结果也要区分“没有数据”和“工具失败”。前者可能意味着查询条件不对，需要改写查询；后者可能是权限、网络或服务故障，需要走错误处理。若两者都返回空字符串，模型就很难做出正确判断。

#### 8. 终止条件和人工接管

Agent 的完成条件不能只写成“模型认为任务完成”。可以组合使用几种条件：必须字段全部生成、引用数量达到最低要求、程序校验通过、工具调用次数未超限，以及用户确认已完成。

当出现连续两次相同工具调用、计划没有进展、证据互相冲突、权限不足或超过预算时，应停止循环并进入人工接管。对用户呈现时要说明已经完成了什么、卡在哪里、需要用户补充什么，而不是返回一段模糊的失败信息。

#### 9. 如何测试 Agent Loop

测试不能只测最终文本，还要测中间行为。可以准备一组固定任务，分别验证：是否选择了正确工具、参数是否符合 Schema、权限不足时是否拒绝、工具超时时是否有限重试、重复执行是否幂等、达到上限时是否停止，以及最终答案是否包含必要来源。

在评测结果中，工具调用正确但最终表达不够好，和最终文本流畅却调用了错误数据源，应该被视为两类问题。前者优先优化提示和输出模板，后者要检查工具描述、路由规则和权限边界。

### 继续追问

**Q：为什么不能让 LLM 直接访问数据库？**  
因为 SQL、权限、数据脱敏和查询成本都需要受控。更安全的做法是暴露受限查询工具。

**Q：工具结果应该返回多少？**  
返回模型下一步真正需要的最小证据。大日志应当裁剪，完整内容可以保存为外部工件供后续检索。

**Q：Agent Loop 最常见的失败原因是什么？**  
工具 Schema 不清晰、工具权限过宽、没有终止条件、上下文太长，以及没有区分临时故障和危险动作。

### 面试总结

不要只背“模型、工具、记忆”这几个名词，要讲完整运行时：目标、模型、工具、执行边界、状态、循环、治理和 Trace。模型负责决策意图，运行时负责验证和执行。

## 03 ReAct、Plan-and-Execute、Reflection 如何选型？

### 面试官追问

**面试官：** 说说 ReAct、Plan-and-Execute、Reflection 三种范式的区别。项目里你会怎么选？

**我：** ReAct 是边想边做，Plan-and-Execute 是先规划再执行，Reflection 是执行后反思。

**面试官：** 这三个是互斥的三套系统吗？如果一个长任务需要先规划，但每个步骤内部还要根据工具结果调整，应该怎么组合？Reflection 是完整流程，还是一种质量增强能力？

真正要讲清楚的是：每种范式在解决什么问题，以及加入它之后增加了什么成本。

### 常见错误回答

“简单任务用 ReAct，复杂任务用 Plan-and-Execute，高质量任务用 Reflection。”

这只是口诀，缺少流程漂移、动态重规划、质量标准、额外延迟和失败处理等工程内容。

### 30 秒简答

ReAct 是“思考、行动、观察、再思考”的循环，灵活而且实现简单，适合中小型的不确定任务，但长任务容易跑偏。

Plan-and-Execute 把规划和执行拆开，先确定任务阶段，再逐步执行，适合依赖关系复杂、需要并行或需要整体结构的长任务，但计划需要支持动态修改。

Reflection 是对结果进行检查和修正的质量控制环节，通常叠加在 ReAct 或 Plan-and-Execute 上，而不是独立替代它们。选型主要看任务复杂度、流程确定性、质量要求、成本和延迟。


### 原理拆解

#### 1. ReAct：根据最新结果决定下一步

```text
思考 -> 行动 -> 观察 -> 思考 -> 行动 -> ... -> 完成
```

每一步都基于上一步的工具结果重新判断。如果搜索没有结果，可以改查询；如果接口失败，可以选择重试或换工具。

它的优点是灵活、容易实现、每一步都比较透明。缺点是缺少全局计划，面对长任务可能重复调用、忘记目标或在局部问题上消耗过多 Token。

#### 2. Plan-and-Execute：先建立全局路线

```text
目标 -> 生成计划 -> 执行步骤 -> 检查进度 -> 必要时重规划 -> 输出
```

它适合研究报告、跨数据源分析和多阶段交付。计划应该包含任务 ID、依赖、输出和验收条件，而不是一段看起来很完整的自然语言。

计划是对任务的假设，不是不可修改的合同。数据源不存在、工具失败或新证据出现时，需要支持 Replan。

#### 3. Reflection：检查结果是否达到标准

Reflection 需要一套评价标准，例如：

- 是否回答了用户提出的全部问题；
- 关键结论是否有来源；
- 输出格式是否符合要求；
- 是否包含不应暴露的数据；
- 计算结果是否通过程序校验。

如果没有明确的评价标准，只让另一个模型说“这份答案不错”，并不能真正证明答案正确。

#### 三种范式对比

| 范式 | 主要解决的问题 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| ReAct | 下一步不确定 | 灵活、实现成本低 | 长任务容易漂移 |
| Plan-and-Execute | 多阶段任务缺少全局结构 | 依赖清晰、便于并行 | 规划成本和计划僵化 |
| Reflection | 结果质量不稳定 | 可发现缺漏并修正 | 增加调用、延迟和成本 |

### 企业协作场景

用户提出：“调查本月续费风险上升的原因，并写一份管理层简报。”

- 用 **Plan-and-Execute** 拆出数据收集、文档检索、趋势分析和报告生成。
- 在每个检索步骤中用 **ReAct**，因为一次搜索结果会影响下一次查询。
- 交付前加入 **Reflection**，检查每个数字是否有证据、结论是否超出数据、是否泄露敏感内容。

三种能力可以组合，不需要强行选择一套“最先进”的范式。

### 工程方案与取舍

1. 任务短、工具结果不确定时，先用 ReAct。
2. 有多个依赖步骤、需要并行或阶段性产物时，使用 Plan-and-Execute。
3. 只有在“错误能被定义和检测”时才加入 Reflection。
4. 为重规划设置次数上限，避免计划不断变化。
5. 用质量提升和延迟、成本的变化做评估，不要默认第二次模型调用一定值得。

确定性业务规则应当用代码或校验器完成，不能只让 Agent 自己反思。例如金额、权限、合规和引用完整性，都应该尽量有程序化检查。

#### 5. 三种范式如何组合

一个常见的生产组合是：外层使用 Plan-and-Execute 管理阶段，阶段内部使用 ReAct 处理动态检索，最终使用 Reflection 或程序校验做质量控制。

```text
生成阶段计划
-> 并行执行资料收集任务
   -> 每个任务内部 ReAct 检索和补查
-> 汇总结构化证据
-> 规则校验与 Reflection
-> 不合格则定向修正
-> 输出报告
```

组合时要避免重复规划。外层计划器只负责阶段和依赖，Worker 内部只解决自己的局部问题；审查环节只指出具体缺陷，不要重新生成一份完全不同的任务计划。每一层职责越清楚，越容易定位问题。

#### 6. 计划需要结构化和可变更

计划最好不是一段自然语言，而是类似下面的结构：

```json
{
  "steps": [
    {"id": "collect_data", "depends_on": [], "done_when": "数据覆盖本月"},
    {"id": "analyze_reason", "depends_on": ["collect_data"], "done_when": "每个结论有证据"},
    {"id": "write_report", "depends_on": ["analyze_reason"], "done_when": "通过格式校验"}
  ]
}
```

执行器可以据此判断哪些任务可并行、哪些任务被阻塞，以及哪一步需要重试。若发现关键数据源不存在，应把原计划标记为失效，并记录重规划原因。重规划不是简单地再次请求模型，而是把当前已完成结果、失败原因和剩余预算传给计划器。

#### 7. Reflection 的边界

Reflection 最适合发现“可观察的缺陷”，例如漏答、格式错误、引用缺失和结论与证据不一致。它不适合单独判断真实世界事实，也不能代替权限和合规系统。

比较稳妥的做法是让审查器输出结构化结果：

```text
passed: false
issues: [引用缺失, 一个数字无法在来源中找到]
severity: high
repair_action: 重新查询销售数据并补充引用
```

只有低风险、可自动修复的问题才允许 Agent 自己回到执行环节。涉及敏感信息、金额或对外发布时，应进入人工确认。这样 Reflection 是质量闸门，而不是让模型无限自我循环。

#### 8. 选型时如何做实验

可以用同一批任务比较三种配置：纯 ReAct、Plan-and-Execute、组合方案，观察完成率、关键步骤正确率、引用覆盖率、平均轮数、P95 延迟和成本。还要记录失败类型，而不是只看总分。

如果任务大部分只需要两三次工具调用，加入复杂计划器可能得不偿失；如果任务包含十几个有依赖关系的步骤，纯 ReAct 的漂移和重复调用就会明显增加。选型应该来自任务分布和实验数据，而不是来自范式名称的先进程度。

### 继续追问

**Q：Reflection 和重试有什么区别？**  
重试是临时失败后的再次执行；Reflection 是根据评价标准找出结果缺陷，并改变下一次生成或执行策略。

**Q：什么时候计划应该由代码写死？**  
涉及审批顺序、权限、金额阈值和合规流程时，路线应该由代码控制，模型只负责其中的不确定步骤。

**Q：怎么防止审查 Agent 自己胡编一套评价？**  
给它明确证据、结构化评价字段和规则校验，不能把另一个模型的判断直接当成事实来源。

### 面试总结

回答时抓住“控制”这个关键词：ReAct 是局部动态控制，Plan-and-Execute 是全局路线控制，Reflection 是质量控制。生产项目通常是先规划路线，在步骤内部 ReAct，交付前再按照明确标准检查。

## 04 复杂任务的拆分、规划、记忆与上下文管理

### 面试官追问

**面试官：** 复杂任务怎么让 Agent 稳定完成？任务拆分、规划、记忆和上下文管理分别怎么做？

**我：** 把大任务拆成小任务，让模型自己规划，再把对话存到记忆里。

**面试官：** 哪些内容应该拆开，哪些必须放在一起？计划和记忆是一回事吗？为什么把所有历史都保存下来，模型还是会越做越乱？下一轮请求到底应该放哪些信息？

这几个概念经常一起出现，但它们解决的不是同一个问题。

### 常见错误回答

“把上下文窗口调大，把全部聊天历史存到向量数据库里，问题就解决了。”

上下文越长不代表答案越好。旧信息可能过期，工具日志可能淹没当前目标，未经筛选的记忆还可能引入隐私和错误事实。

### 30 秒简答

我会把四件事分开：任务拆分负责把目标拆成可验证的工作单元；规划负责安排依赖和执行顺序；记忆负责保存可能跨步骤或跨会话复用的信息；上下文管理负责选择当前这一次模型调用真正需要看到的内容。

处理复杂任务时，我会用结构化状态记录任务、依赖、证据和失败原因，使用摘要或外部工件代替完整历史，并给每一步设置输入、输出、验收条件、超时和重试边界。


### 原理拆解

#### 1. 任务拆分：把目标变成可检查的工作单元

一个合格的子任务，应该具备：

```text
输入 -> 预期输出 -> 依赖关系 -> 验收条件 -> 失败处理
```

例如“写一份竞品分析”不应该是一个黑盒任务，可以拆成：收集资料、提取可比指标、处理冲突、形成结论、生成报告。

静态拆分由工程师提前定义，适合稳定流程；动态拆分由模型根据目标生成，适合开放任务，但必须限制工具范围、任务数量和停止条件。

#### 2. 规划：决定顺序、依赖和备选路线

计划不是一段看起来很完整的解释，而是可以执行的状态：任务 ID、依赖、状态、工具和交付物都应该能被系统读取。

如果某个数据源不可用，系统需要知道是阻塞、换来源、重试，还是向用户追问，而不是继续生成一份看起来完整但没有证据的报告。

#### 3. 记忆：有选择地保存可复用信息

| 类型 | 示例 | 适合的保存方式 |
| --- | --- | --- |
| 工作记忆 | 当前计划、最新工具结果 | 结构化任务状态 |
| 对话记忆 | 最近的用户约束 | 滚动窗口或摘要 |
| 情节记忆 | 一次任务的结果和失败原因 | 带时间的事件记录 |
| 语义记忆 | 长期偏好、稳定规则 | 经过筛选的知识记录 |

记忆必须考虑来源、时间、置信度、权限、更新和删除。没有这些字段的“永久记忆”，很容易把临时信息变成长期错误。

#### 4. 上下文管理：控制模型当前看到什么

一次模型调用通常只需要：当前目标、当前计划步骤、相关工具 Schema、必要证据、状态摘要和安全要求。

可以使用滑动窗口保存最近对话，用摘要压缩已完成部分，用检索召回长期知识，把大文档和长日志保存为外部工件。不要每一轮都把全部原始消息重新塞进 Prompt。

### 企业协作场景

用户说：“请根据项目文档、群聊和进度表，整理本周项目风险，并给出负责人和截止时间。”

可以拆成：

```text
1. 确定项目范围和统计周期
2. 检索授权文档与相关讨论
3. 查询里程碑、负责人和进度数据
4. 提取风险证据并合并重复项
5. 根据规则判断风险等级
6. 生成风险报告和拟议任务
7. 校验引用，确认后再创建任务
```

计划状态保存任务完成情况和证据 ID。长期记忆可以保存团队的报告格式偏好，但不应该默认永久保存群聊中的所有内容。

### 工程方案与取舍

| 选择 | 好处 | 代价 |
| --- | --- | --- |
| 任务切得更细 | 更容易重试和校验 | 编排节点更多 |
| 任务切得更粗 | 调用少、链路短 | 出错难定位、恢复粒度大 |
| 保留完整历史 | 细节不容易丢 | 成本高、噪声大、隐私风险高 |
| 摘要压缩 | 上下文更短 | 可能丢掉后来有用的细节 |
| 向量记忆 | 语义召回方便 | 可能召回错误或过期信息 |
| 结构化状态 | 执行更稳定 | 需要维护明确的字段和合并规则 |

比较稳妥的默认方案是：结构化状态管理当前任务，带来源的检索管理知识，摘要管理对话连续性。

#### 5. 用状态机管理复杂任务

复杂任务最好有明确状态，而不是让模型通过阅读历史猜当前进度。例如：

```text
created -> planning -> collecting -> analyzing -> waiting_approval -> completed
                         |             |
                         v             v
                      blocked        failed
```

每个状态都应该定义允许的下一步。处于 `waiting_approval` 时，系统只能展示草稿或等待确认，不能因为模型再次输出“继续执行”就直接创建任务。处于 `blocked` 时，需要记录阻塞原因和用户需要补充的信息。

状态机的价值在于可恢复和可回放。服务重启后可以从最后一个已确认状态继续；出现投诉时，也能还原 Agent 当时看到了哪些证据、执行了哪些动作。

#### 6. 记忆的读写都要有门槛

记忆不是越多越好，写入前要判断这条信息是否稳定、是否来自可信来源、是否允许跨会话使用、是否可能包含敏感信息。读取时也要判断它是否与当前任务相关、是否已经过期、是否与最新数据冲突。

例如用户说“这次报告先按简版输出”，这是当前任务约束，不应该自动变成永久偏好；用户多次确认“我负责支付业务项目”，并且信息来源可靠，才可能沉淀为长期偏好，但仍应支持用户修改和删除。

建议给记忆增加来源、创建时间、更新时间、有效期、置信度和权限范围。召回结果还要允许被最新的业务数据覆盖，不能因为向量相似度高就把旧记忆当成当前事实。

#### 7. 上下文预算怎么分配

可以把上下文看成有限预算，优先级通常是：当前用户目标和硬约束、当前步骤输入、必要工具定义、最新可靠证据、任务状态摘要、相关历史偏好。低优先级的闲聊、重复日志和已经验证过的中间过程应当被压缩或移出。

一种常见策略是“摘要加引用”：把已经完成的长过程压缩成结论、证据 ID 和未解决问题，原始内容保存到外部工件。后续需要细节时，再根据证据 ID 定向读取，而不是每次把全部原文带回模型。

上下文压缩后必须做信息保真检查，尤其是数字、否定条件、时间范围和责任人。摘要把“尚未确认”压成“已经确认”，会比单纯超长更危险。

#### 8. 如何评估拆分和上下文策略

可以从任务完成率、子任务独立成功率、重试恢复率、上下文长度、单轮成本、引用准确率和过期信息误用率等方面评估。对同一个任务分别使用完整历史、摘要历史和结构化状态，比较模型是否能正确找到当前步骤和关键证据。

如果拆分后每个节点都很短，但节点之间频繁传递大量文本，说明拆分粒度可能过细；如果一个节点失败后必须从头开始，说明任务边界和中间产物设计得不够好。好的拆分应该让局部失败只影响局部，不让整个任务失去进度。

### 继续追问

**Q：任务拆到什么粒度最合适？**  
拆在“可以独立校验、重试或并行”的地方。紧密耦合的推理步骤不要为了增加节点而强行拆开。

**Q：如何避免上下文超限？**  
限制工具输出大小，保存大内容为外部工件，摘要已完成步骤，只召回相关信息，并给当前目标和安全规则预留空间。

**Q：失败经历都应该存进长期记忆吗？**  
不应该。只有经过验证、明确适用范围并且没有过期风险的经验，才适合沉淀为长期记忆。

### 面试总结

一定要把四个概念分开：拆分定义工作单元，规划决定路线，记忆保存可复用信息，上下文管理决定模型此刻看到什么。Agent 不是靠无限加长 Prompt 变稳定，而是靠紧凑、结构化、可验证的状态变稳定。

## 05 Single-Agent 和 Multi-Agent 怎么选？

### 面试官追问

**面试官：** 什么情况下使用 Multi-Agent，而不是一个 Single-Agent？多个 Agent 怎么通信和协作？

**我：** 复杂任务可以拆给不同 Agent，一个负责搜索，一个负责写作，这样会更快。

**面试官：** 一个 Agent 不能调用两个工具吗？如果两个 Agent 搜索了同一批资料，谁负责避免重复？如果研究 Agent 失败了，谁决定重试、换路线，或者告诉写作 Agent 证据不完整？

Multi-Agent 不是“Agent 越多越智能”，而是一种需要付出协作成本的架构选择。

### 常见错误回答

“复杂任务就用 Multi-Agent，因为不同 Agent 可以分工。”

分工只是起点。没有任务所有权、消息协议、状态合并和结束条件，多个 Agent 只会把重复工作、调用成本和排错难度一起放大。

### 30 秒简答

我会默认先用 Single-Agent。只要一个 Agent 能处理当前上下文、工具数量和执行路径，就不需要引入额外的协调系统。

当任务存在明确的角色边界、可以并行的子任务、不同的工具或权限域，或者确实需要独立审查时，再考虑 Multi-Agent。

生产实现通常采用 Supervisor-Worker 结构：协调 Agent 负责拆任务、分配任务、合并证据和判断整体完成；专业 Agent 只负责边界清晰的子任务，并返回结构化结果、状态和证据，而不是一段不可解析的长对话。


### 原理拆解

#### 1. Single-Agent 是默认方案

一个 Agent 本来就可以使用多个工具、运行多轮循环和维护任务计划。Single-Agent 的上下文集中、状态简单、测试方便，也是最容易做权限和 Trace 的方案。

适合以下情况：任务较短、信息强相关、权限一致、工具数量有限，或者系统还处于验证阶段。

#### 2. Multi-Agent 解决真正的隔离问题

只有出现下面一类问题时，多 Agent 才更有价值：

- 多个子任务互相独立，可以并行执行；
- 不同角色需要不同工具或数据权限；
- 需要让审查者独立检查作者的结果；
- 长任务需要隔离上下文，避免所有内容堆在一个窗口；
- 专业能力需要独立替换或扩展。

如果只是因为“图画出来更复杂”，就增加 Agent，通常属于过度设计。

#### 3. Supervisor-Worker 协作

```text
协调 Agent
-> 创建带边界的子任务
-> 分配给专业 Agent
-> 接收状态、证据和结果
-> 合并并处理冲突
-> 判断下一步或结束
```

协调者可以借助模型规划，但仍然需要确定性限制：允许使用哪些 Worker、消息格式是什么、超时多久、最多重试几次、什么条件算完成。

#### 4. 共享状态与隔离状态

不要把全部历史默认共享给所有 Agent。Worker 只需要拿到任务目标、输入范围和必要证据；共享状态应该有明确 Schema 和合并规则。

例如证据列表可以追加，但最终结论不能允许多个 Agent 随意覆盖，应该由协调者或显式的评审规则统一写入。

### 企业协作场景

管理层想要一份月度经营分析，数据来自项目文档、进度表、客户反馈和风险记录。

可以设计为：

```text
协调 Agent：拆任务、控制预算、负责最终报告
数据分析 Agent：查询指标、识别异常变化
知识检索 Agent：查找制度和项目证据
客户反馈 Agent：归纳高频问题和主题
审查 Agent：检查引用、事实和敏感信息
写作 Agent：把确认后的证据整理成报告
```

数据分析 Agent 返回指标、时间范围和来源；检索 Agent 返回证据引用；写作 Agent 不负责自己补事实；协调 Agent 负责冲突合并和最终交付。这样每个角色的输出都能被验证。

### 工程方案与取舍

| 维度 | Single-Agent | Multi-Agent |
| --- | --- | --- |
| 实现复杂度 | 低 | 高，需要协调和协议 |
| 上下文 | 集中统一 | 可按角色隔离 |
| 延迟 | 适合串行 | 独立任务可以并行 |
| 成本 | 相对可控 | 模型调用和通信更多 |
| 排错 | 一条主链路 | 需要追踪跨 Agent 消息 |
| 权限 | 一个边界 | 每个角色都要最小权限 |

引入第二个 Agent 前，先回答三个问题：它独有的职责是什么？它返回什么结构化产物？它失败或和其他 Agent 冲突时怎么办？如果答不上来，就先不要拆。

#### 5. Agent 之间如何通信

通信协议要围绕任务产物设计，而不是让 Agent 互相转发完整聊天记录。一个子任务消息至少应包含：任务 ID、目标、输入范围、权限范围、截止时间、输出 Schema 和验收条件。

Worker 返回的结果建议包括：状态、结论、证据列表、置信度、失败原因和下一步建议。例如数据分析 Agent 不应该只返回“销售下降了”，而应该返回指标、统计周期、对比基线、数据来源和异常判断依据。

结构化协议有两个好处：协调者可以自动检查结果是否完整，未来也可以替换 Worker 的实现而不改变整个系统。对大段原文可以通过工件 ID 引用，避免在 Agent 之间反复复制上下文。

#### 6. 并行执行不等于随意并发

只有输入互不依赖、写操作不会相互覆盖的任务才适合并行。例如读取项目文档、查询客户反馈和计算指标可以并发；更新同一条业务记录、修改同一个计划状态则需要串行或加锁。

协调器还要设置并发上限、超时时间和取消机制。某个 Worker 已经产出足够结果时，可以取消尚未开始的低优先级任务；如果一个关键 Worker 超时，协调器需要决定降级、换工具、重试还是中止，而不是让其他 Agent 无限等待。

#### 7. 失败、冲突和恢复

多 Agent 系统至少要区分三种失败：Worker 自身执行失败、返回结果不符合协议、不同 Worker 的结论发生冲突。协议错误可以要求 Worker 按 Schema 重试，工具临时失败可以有限重试，事实冲突则要保留来源并发起补查或人工确认。

协调者最好维护一个任务注册表，记录每个子任务的状态、尝试次数、输入版本和产物版本。这样在恢复时只重跑失败或受影响的节点，不必让全部 Agent 从头开始。

对有副作用的操作，建议把“分析”和“执行”分成不同角色。写作 Agent 可以生成任务草稿，执行 Agent 在获得用户确认和权限校验后才真正写入系统。多 Agent 不应该通过互相说服来决定是否执行危险动作。

#### 8. 权限和评估要按 Agent 分开

每个 Agent 都应使用最小权限。例如检索 Agent 只能读取授权范围内的文档，数据 Agent 只能访问聚合指标，写入 Agent 才能创建任务，但不能读取不相关的客户隐私。权限不能因为请求经过 Supervisor 就全部放大。

评估时除了看最终报告，还要看任务分配准确率、重复任务比例、并行收益、消息传输量、冲突解决率、单任务成本和人工接管率。很多 Multi-Agent Demo 的最终文本不错，但实际调用次数过多、失败无法回放，生产价值并不高。

如果 Single-Agent 在同一数据权限和工具集合下已经能稳定完成任务，拆成多个 Agent 通常只会增加通信和协调开销。只有当隔离带来的收益能够覆盖这些成本时，架构升级才有意义。

### 继续追问

**Q：如何避免多个 Agent 重复工作？**  
由协调者创建任务 ID、输入范围、负责人和完成条件，Worker 只能在自己的任务范围内执行，并通过任务注册表同步状态。

**Q：多个 Agent 的结果冲突怎么办？**  
保留各自来源和置信度，由规则、审查者或协调者发起补充检索。不能简单地把两段矛盾答案拼在一起。

**Q：Multi-Agent 一定更快吗？**  
不一定。只有子任务相互独立，且并行收益大于规划、通信和合并成本时，才会更快。

### 面试总结

Single-Agent 是默认方案，Multi-Agent 适用于真正存在职责、权限、上下文或并行隔离需求的场景。成熟的多 Agent 系统必须具备明确任务协议、结构化证据、状态合并规则、失败处理和整体完成者。

# 02-飞书 Agent 场景设计

## 02-01 智能知识问答 Agent 怎么设计？

### 面试官追问

**面试官：** 如果让你设计一个放在飞书里的企业智能知识问答 Agent，你会怎么做？

**我：** 用户在飞书里提问，Agent 去搜索知识库，然后让大模型生成答案。

**面试官：** 这听起来只是一个 RAG。它和普通知识库搜索有什么区别？用户只能看到自己有权限的文档吗？如果检索不到答案怎么办？回答里的引用可靠吗？

这道题真正考察的，不是你能不能说出“向量数据库、Embedding、Rerank”这些词，而是你能不能把一个企业问答场景讲完整：用户是谁、能看什么、去哪里找、答案从哪里来、结果不可靠时怎么办，以及系统如何上线后持续变好。

### 常见错误回答

“把飞书文档全部切成向量，用户提问后做相似度搜索，再让大模型回答。”

这句话只能说明你知道 RAG 的基本链路，但还没有达到企业 Agent 的设计要求。企业知识问答最容易出问题的地方，往往不是模型不会回答，而是搜到了用户不该看的内容、引用和结论对不上、旧文档覆盖了新制度，或者没有答案时模型仍然自信地编造。

### 30 秒简答

我会把它设计成一个带权限控制和引用溯源的企业知识问答 Agent。用户在飞书 IM 中提问后，系统先识别用户身份、租户和可访问范围，再根据问题判断应该检索哪些知识源，例如飞书文档、知识库、云盘或多维表格。

检索层负责召回和排序，生成层只能基于检索到的证据回答，并返回引用位置。如果证据不足，系统应该明确说明不知道、向用户追问或转人工，而不是强行生成答案。Agent 的价值在于根据问题类型选择检索路径、改写查询、补充搜索和整理多来源证据；权限、引用、审计和最终安全边界必须由系统控制。


### 原理拆解

#### 1. 先定义它解决的不是“聊天”，而是知识获取问题

企业员工问“报销标准是什么”“某项目当前风险有哪些”“新员工入职流程在哪里”，本质上是在寻找可信、最新、与自己权限匹配的信息。

因此，系统目标不能只写成“回答问题”，至少要拆成四个结果：

```text
找到相关知识
-> 确认用户有权查看
-> 用证据组织答案
-> 让用户知道答案来自哪里
```

如果只追求语言流畅，系统很容易变成“看起来很聪明的内部搜索框”。真正可用的问答 Agent 必须同时关注答案正确性、权限安全、引用完整性和失败时的诚实程度。

#### 2. 飞书里的数据源不是一个统一的知识库

企业信息可能分散在不同位置：正式制度在知识库或云文档里，项目进度在多维表格里，会议结论在会议纪要里，临时决策在群聊消息里。

不同数据源的特点不同：

| 数据源 | 适合回答的问题 | 主要风险 |
| --- | --- | --- |
| 飞书文档 | 制度、方案、说明和正式知识 | 版本过期、权限继承复杂 |
| 知识库 | 结构化沉淀的长期知识 | 节点层级和更新状态不一致 |
| 云盘文件 | PDF、表格和历史材料 | 解析质量、重复文件 |
| 多维表格 | 项目、人员、状态和统计数据 | 字段语义、实时性和行级权限 |
| 群聊与会议纪要 | 临时结论和上下文 | 噪声大、信息未经确认 |

Agent 不应该把所有来源不加区分地混在一起。它需要根据问题判断数据源优先级：制度问题优先正式文档，当前状态问题优先结构化数据，临时讨论只能作为补充证据。

#### 3. 权限过滤必须发生在检索前或检索过程中

最危险的错误是“先把所有文档召回，再让模型判断哪些能展示”。模型不是权限系统，不能依靠 Prompt 让它稳定地识别越权内容。

更可靠的链路是：

```text
识别用户身份
-> 获取租户、部门、角色和资源权限
-> 将权限条件写入检索过滤器
-> 只召回用户有权访问的内容
-> 生成答案并保留来源
```

如果一个文档用户无权访问，即使它和问题高度相关，也不应该进入模型上下文。对于多维表格，还要进一步考虑表级、视图级甚至记录级权限。权限过滤要在应用层和数据源层分别校验，不能只依赖前端隐藏按钮。

#### 4. Agent 和普通 RAG 的差别在哪里

普通 RAG 通常是一条比较固定的链路：问题向量化、召回文档、重排、生成答案。它适合问题清晰、数据源单一的场景。

知识问答 Agent 会增加一层任务判断：

- 这是制度查询，还是项目状态查询？
- 应该查文档、表格，还是会议纪要？
- 当前结果是否足够？是否需要改写问题继续搜索？
- 多个来源是否互相矛盾？需要不要提示时间和版本？
- 用户真正想要的是答案、对比、摘要，还是后续行动？

但这不意味着所有问答都应该做成自由规划的 Agent。简单 FAQ 可以直接走固定 RAG，只有涉及多来源检索、查询澄清、结果比较或后续动作时，才引入更强的动态决策。

#### 5. 检索结果必须能支撑最终结论

生成层不能只拿到一堆相似文本。每条证据最好带上标题、文档链接、章节、更新时间、权限范围和相关片段。

例如回答“今年差旅住宿标准是多少”时，系统不仅要给金额，还应该引用制度名称和生效时间。如果检索到了两份版本不同的制度，Agent 应该展示冲突，优先采用最新生效版本，或者提示用户确认，而不是把两份内容混合成一个看似完整的数字。

可以把答案分成三层：

```text
结论：直接回答用户问题
依据：列出支持结论的文档或数据
边界：说明时间、权限、冲突和不确定性
```

#### 6. 没有答案时要有明确的失败路径

企业问答最重要的能力之一，是知道什么时候不能回答。

- **没有召回结果：** 改写查询或请用户补充关键词。
- **召回结果相关性低：** 告知暂时没有找到可靠依据。
- **来源互相冲突：** 展示冲突文档和更新时间。
- **用户无权访问：** 只提示权限不足，不泄露文档标题和内容。
- **问题需要人工判断：** 转给知识负责人或业务人员。
- **涉及高风险决策：** 只能提供资料，不直接替用户做最终决定。

失败处理不能只写一句“请重新提问”。系统应该记录失败类型，后续用于优化切分、检索、权限映射和知识库更新。

### 企业协作场景

用户在飞书中提问：“今年销售人员出差住宿标准是多少？如果是外地项目，能不能走特殊审批？”

系统可以先识别这是制度查询，并检索差旅制度、特殊审批说明和相关流程文档。回答时给出当前有效标准、引用的制度段落和审批入口。如果用户继续问“帮我发起审批”，系统再进入写操作流程，重新确认身份、审批类型和所需字段。

这里要把“回答”和“执行”分开：知识问答阶段只读数据并提供证据，发起审批属于另一条受权限和确认控制的流程。不要因为 Agent 能查到制度，就默认它可以替用户直接提交审批。

### 工程方案与取舍

1. **先从正式文档和知识库做 MVP。** 群聊内容噪声和权限复杂度更高，可以后续逐步接入。
2. **召回策略采用混合检索。** 关键词适合制度名称和专有名词，向量检索适合语义表达，Rerank 用于最终排序。
3. **权限过滤前置。** 不让无权内容进入模型上下文，避免从根上产生越权泄露。
4. **答案必须带引用。** 对制度、流程和数字类问题尤其重要。
5. **保留检索与生成 Trace。** 出现错误时要知道是切分错、召回错、权限错，还是模型引用错。
6. **先做只读问答。** 等准确率、引用率和权限校验稳定后，再接入创建任务、发消息和发起审批等动作。

#### 7. 如何评估这个 Agent 是否真的有效

不能只看用户觉得“回答自然不自然”。至少要建立一组包含权限、版本冲突、无答案和跨来源查询的测试集，评估：

- 检索召回率和相关性；
- 答案是否被证据支持；
- 引用链接是否正确；
- 越权内容是否被拦截；
- 无答案时是否拒答；
- 用户问题的一次解决率；
- 平均响应时延和单次成本；
- 转人工比例和用户满意度。

线上还要抽样回放失败问题，观察是知识没有沉淀、文档过期、权限映射错误，还是 Agent 选择了错误的数据源。评测集应该持续加入真实失败样本，而不是上线前写完就不再更新。

### 继续追问

**Q：智能知识问答 Agent 和 RAG 有什么关系？**  
RAG 是知识增强的一条技术链路，Agent 是围绕目标选择数据源、规划检索、处理结果和决定下一步的执行系统。简单问答可以只用 RAG，复杂多来源任务才需要 Agent。

**Q：为什么不能把所有飞书文档都放进向量库？**  
需要考虑权限、版本、删除同步、重复内容和数据源优先级。没有权限过滤的全量向量库可能造成越权泄露。

**Q：模型回答错了，应该先换模型吗？**  
不一定。先定位是数据解析、切分、召回、排序、权限、引用还是生成问题，再决定优化检索、Prompt、模型或数据治理。

**Q：用户问到没有权限的文档，应该怎么提示？**  
只能提示当前账号没有访问权限，不能透露文档标题、内容、作者或是否存在敏感信息。

### 面试总结

设计飞书智能知识问答 Agent 时，回答顺序可以是：先讲用户问题和数据源，再讲身份权限、检索召回、证据引用、答案生成和失败处理，最后补充评测、审计和上线策略。

核心原则是：让 Agent 帮助系统处理不确定的检索和整理，让权限系统控制用户能看什么，让证据决定答案能说什么。一个真正可上线的企业问答 Agent，不是“接上向量库就能聊天”，而是一个具备权限边界、引用溯源、版本意识和失败兜底的知识服务系统。

## 02-02 文档总结与会议纪要 Agent 怎么设计？

### 面试官追问

**面试官：** 如果让你设计一个自动整理飞书文档、会议录音和会议纪要的 Agent，你会怎么做？

**我：** 把会议转成文字，然后让大模型总结重点，最后生成会议纪要。

**面试官：** 总结和纪要有什么区别？模型怎么知道哪些是已经确定的决定，哪些只是讨论？行动项的负责人和截止时间不明确时怎么办？生成的纪要可以直接发到群里吗？

这道题真正考察的，不是你会不会调用一个总结接口，而是你能不能把非结构化内容变成可追踪的工作结果：讨论了什么、决定了什么、谁要做什么、哪些问题还没有结论，以及发布前如何让参与者确认。

### 常见错误回答

“把会议文本丢给大模型，让它总结成几条重点，再自动发给参会人。”

这句话忽略了会议内容中最难的部分：发言人识别、上下文切分、结论和观点区分、行动项抽取、时间与责任人确认，以及敏感内容的权限控制。会议纪要不是越短越好，而是要让后续的人能据此行动和追溯。

### 30 秒简答

我会把它设计成一个“内容理解 + 结构化提取 + 人工确认 + 文档发布”的会议纪要 Agent。系统先获取经过授权的会议转写、议程、相关文档和聊天记录，再按议题切分内容，识别讨论、决定、风险、待办和未决问题。

模型负责理解语言、提炼重点和生成草稿，但不能自行确认事实，也不能在没有授权的情况下把纪要发到群里。每条决定和行动项都应保留来源片段，负责人和截止日期不明确时要标记待确认。生成草稿后，由主持人或指定人员审核，确认后再写入飞书文档并通知相关人员。


### 原理拆解

#### 1. 摘要和会议纪要不是一回事

摘要的目标是压缩信息，让读者快速了解内容；会议纪要的目标是记录事实、决定和后续行动，方便团队继续推进。

一份可执行的会议纪要至少应该包含：

```text
会议主题与时间
-> 参与人和议程
-> 关键讨论
-> 已确认决定
-> 行动项、负责人、截止时间
-> 风险与未决问题
-> 原始依据和相关链接
```

如果只输出“本次会议讨论了三个重点”，读者仍然不知道谁负责、什么时候完成、哪些结论已经生效。因此，Agent 的输出 Schema 应该在生成前定义好，而不是让模型自由发挥格式。

#### 2. 输入数据需要先做清洗和对齐

会议内容可能来自妙记转写、在线会议字幕、群聊消息、共享文档和会前材料。不同来源会有重复、口语化、识别错误和时间线不一致的问题。

处理链路可以是：

```text
获取授权内容
-> 去除无意义口头语和重复片段
-> 进行说话人和时间戳对齐
-> 按议程、时间或主题切分
-> 关联会前文档和历史决策
-> 交给模型做结构化提取
```

不能把所有历史材料不加筛选地塞进上下文。会前材料用来补充背景，会议转写用来确认实际讨论，历史纪要用来比较变化，三者的证据等级要区分。

#### 3. 如何区分讨论、决定和行动项

会议里常见这样的表达：“我们可以考虑下周上线”“这个方向大家应该都没问题”“那就先由小王看一下”。这些话不一定代表正式决定，也不一定足以生成任务。

Agent 可以根据语言线索和上下文进行初步判断，但最终要保留状态：

- **讨论中：** 观点、假设、候选方案和反对意见。
- **已决定：** 明确表达的结论、通过的方案或主持人确认的结果。
- **待确认：** 责任人、截止时间或决策依据不完整。
- **行动项：** 具体动作、负责人、时间和验收标准清晰。
- **未决问题：** 会议结束时仍没有结论的问题。

这比简单把所有“将要做”都变成任务更安全。否则系统会把一句随口讨论变成正式待办，反而给团队制造噪声。

#### 4. 引用和时间戳决定纪要是否可信

每条重要结论最好都带上来源，例如会议时间戳、文档章节或群消息链接。对于“预算增加”“上线时间变更”“负责人调整”等高影响内容，应该能够一键回到原始发言。

可以将纪要内容组织成：

```text
结论：发生了什么
依据：哪段原始内容支持它
状态：已确认、待确认或存在冲突
动作：接下来谁在什么时候做什么
```

如果转写中出现“下周一”和“下周二”两种说法，Agent 不应该擅自选择一个，而要在纪要中标记冲突，并交给主持人确认。

#### 5. 纪要发布不能绕过人工确认

自动生成草稿和自动发布是两个不同的风险等级。草稿可以允许模型有一定表达自由，正式发布则需要确认内容、范围和接收人。

至少要提供以下控制：

- 由主持人或指定人员审核；
- 支持逐条修改和删除；
- 标记敏感段落和内部权限；
- 确认发布到哪个文档、群或知识库；
- 发布后保留版本和操作日志。

如果纪要包含绩效评价、人事变动、客户信息或商业计划，不能因为参会人都能看就默认可以发到大群。会议参与权限和目标群权限可能并不相同。

#### 6. Agent 的动态能力放在哪里

固定模板和发布流程应该由 Workflow 控制，模型主要处理不确定的信息理解：

- 根据议程选择不同纪要模板；
- 判断哪些内容需要回查会前文档；
- 发现行动项缺少负责人或时间；
- 对多个版本的结论做对比；
- 生成面向不同角色的摘要。

这样做可以避免把整个会议流程交给模型。Agent 负责理解和整理，确定性的文档写入、通知和版本发布由服务接口完成。

### 企业协作场景

产品评审会结束后，系统自动生成一份纪要草稿，内容包括需求背景、已确认方案、争议点、风险和行动项。它发现“性能问题由后端跟进”没有明确负责人和截止时间，就把这一项标记为待确认，而不是直接创建任务。

主持人修改后确认发布，系统将正式纪要写入项目知识库，只把与每个人相关的行动项分别发送给对应成员，并在文档中保留会议转写和相关设计文档的引用。

### 工程方案与取舍

1. **先做转写文本到结构化纪要。** 说话人识别和音频纠错可以根据实际质量逐步增强。
2. **模板要按会议类型区分。** 站会、项目评审、客户会议和复盘会关注点不同。
3. **结论和待办分开存储。** 纪要是记录，任务是执行对象，两者要通过链接关联。
4. **支持增量生成。** 长会议可以按议程分段总结，结束后再统一合并，避免一次性塞入超长上下文。
5. **对高风险内容默认人工审核。** 不自动发布人事、合同、客户和安全事件相关纪要。
6. **写入操作要幂等。** 同一场会议重复触发时不能创建多份正式纪要或重复发送通知。

#### 7. 如何评估纪要质量

除了摘要相似度，还要评估：决定抽取准确率、行动项召回率、负责人和时间识别准确率、引用正确率、未决问题识别率，以及敏感内容拦截率。

可以邀请业务人员对“是否遗漏关键决定”“是否把讨论误写成结论”“是否能据此执行”进行打分。线上要收集人工修改记录，重点分析模型经常被改动的字段，持续优化模板和提示词。

### 继续追问

**Q：会议纪要可以完全自动发布吗？**  
低风险内部例会可以在明确范围内自动发布，但涉及客户、合同、人事、财务和安全内容时必须人工审核。

**Q：模型把讨论内容当成决定怎么办？**  
要求输出状态和来源，设置“待确认”状态，并通过主持人审核后再转成正式决定。

**Q：行动项没有负责人怎么办？**  
不要猜。标记负责人缺失，向主持人或参会人发起确认。

**Q：长会议超过上下文窗口怎么办？**  
按议程或时间分段总结，再做层级合并，同时保留原始时间戳和引用。

### 面试总结

会议纪要 Agent 的核心不是“把内容缩短”，而是把会议中的讨论、决定、风险和行动项结构化，并让每条重要信息都能回到来源。

回答时要强调：模型生成的是可审核草稿，Workflow 控制发布和通知，权限系统控制谁能看，任务系统负责后续执行。只有这样，会议纪要才不是一段漂亮的总结，而是真正能推动团队工作的协作基础设施。

## 02-03 审批与流程助手 Agent 怎么设计？

### 面试官追问

**面试官：** 如果让你设计一个飞书审批助手，用户可以用自然语言发起请假、报销或采购流程，你会怎么做？

**我：** 用户直接告诉 Agent 想申请什么，Agent 自动识别信息，然后调用审批 API 提交。

**面试官：** 如果字段缺失怎么办？如果用户没有权限怎么办？模型判断“符合审批条件”就可以直接通过吗？重复提交怎么办？

这道题真正考察的，是你能不能分清“理解自然语言”和“执行业务规则”的边界。审批是高风险流程，Agent 可以帮助用户填写和导航，但最终的权限、规则、审批人和状态流转必须由确定性系统控制。

### 常见错误回答

“让大模型识别用户的审批意图，补齐参数，然后调用飞书审批接口就可以了。”

这句话忽略了审批场景的风险。模型可能误判申请类型、猜错金额、选错审批人或重复提交。更严重的是，如果把审批条件写在 Prompt 里，模型就可能在上下文混乱时给出不一致的结果。

### 30 秒简答

我会把审批助手设计成“自然语言入口 + 确定性流程引擎”。Agent 负责识别用户想办理的流程、提取申请字段、查询缺失信息、解释规则并生成申请草稿；后端负责身份、权限、字段、金额、审批链和幂等校验。

在真正提交前，系统必须把申请类型、关键字段、审批人和可能的影响展示给用户确认。提交之后，审批状态由流程系统维护，Agent 只负责查询、解释和通知，不能靠模型直接改变审批结果。


### 原理拆解

#### 1. 审批助手首先是流程入口，不是审批决策者

自然语言适合描述“我下周一到周三请假”“我要报销一笔客户招待费用”，但企业流程需要结构化字段：流程类型、开始结束时间、金额、事由、附件、成本中心和审批人。

Agent 的任务是把自然语言转换成待确认的流程草稿：

```text
理解用户意图
-> 选择流程类型
-> 提取字段
-> 识别缺失项
-> 查询业务规则
-> 生成草稿
-> 用户确认
-> 确定性服务提交
```

“是否符合规则”“应该由谁审批”“是否可以免审”不能由模型自由决定，而应该交给流程配置和后端规则服务。

#### 2. 字段收集要支持多轮补全

用户通常不会一次性提供全部信息。Agent 应该知道哪些字段已经明确，哪些字段缺失，哪些字段需要用户确认。

例如报销申请可能需要：金额、费用类型、发生日期、项目、事由和发票附件。系统可以一次询问一组强相关字段，但不要为了凑参数让模型猜金额、日期或项目编码。

字段状态可以设计成：

- 已确认：用户明确提供或系统可靠读取；
- 待确认：模型从上下文推断但仍需用户确认；
- 缺失：提交前必须补齐；
- 冲突：不同消息或附件中的信息不一致；
- 不适用：当前流程不需要该字段。

只有必填字段全部通过校验，系统才允许进入提交确认页。

#### 3. 业务规则必须在模型之外执行

审批规则可能包括金额分级、部门限制、预算余额、时间冲突、特殊人员范围和附件要求。这些规则应该由规则服务、审批配置或业务后端提供结果，而不是把一段规则全文放进 Prompt 让模型判断。

模型可以把结果解释成人话，例如“该金额需要部门负责人和财务共同审批”，但不能自行改写审批链。如果规则服务返回“预算不足”，Agent 只能向用户说明原因或建议其他流程，不能通过更换描述绕过限制。

#### 4. 提交前确认是高风险边界

以下动作通常需要用户确认：

- 正式提交审批；
- 选择或变更审批人；
- 上传或发送敏感附件；
- 撤回、转交或加急审批；
- 代表用户向其他人发出通知。

确认内容不能只显示“是否提交”，而要展示关键字段、金额、接收人、审批链和副作用。用户确认后，后端仍要重新做一次权限和业务校验，不能把前端确认当成安全边界。

#### 5. 审批状态应该由流程系统维护

提交成功、审批中、已通过、已拒绝、已撤回、系统异常等状态都应该来自审批系统。Agent 可以根据状态解释下一步，但不能因为用户说“已经通过了”就把本地状态改成通过。

查询状态时还要处理延迟和重复事件：如果提交接口超时，不能直接再次提交；应该先用请求幂等键查询原始实例状态，再决定是否重试。

#### 6. Agent 与 Workflow 的组合方式

审批场景非常适合混合架构：

```text
Agent：理解意图、收集字段、解释规则、回答状态
Workflow：校验字段、计算审批链、提交实例、处理状态流转
人工：确认高风险申请和异常情况
```

这比“让 Agent 自己规划整个审批过程”稳定得多。流程稳定的部分由代码保证，语言理解和用户交互由模型增强。

### 企业协作场景

用户在飞书里说：“帮我报销上周客户晚餐，金额 860 元，走项目 A。”

Agent 识别为招待费用报销，提取金额、时间、项目和事由，并发现缺少发票附件。它向用户索取附件，查询项目 A 是否允许该费用类型，生成申请草稿。用户确认后，后端重新校验身份、金额和预算，再创建审批实例。

如果接口返回超时，系统不会直接再次创建，而是先根据幂等键查询是否已经生成审批单，并向用户展示真实状态。

### 工程方案与取舍

1. **先支持少量高频流程。** 请假、报销和加班等流程字段相对稳定，适合先做 MVP。
2. **流程配置和模型 Prompt 分离。** 业务规则变化时不必重新训练或大幅修改 Prompt。
3. **提交前展示完整草稿。** 让用户确认关键字段和副作用。
4. **后端二次校验。** 即使模型和前端已经校验，提交服务仍要重新判断权限和业务规则。
5. **所有提交使用幂等键。** 由用户、流程类型和请求标识共同生成，避免重复实例。
6. **异常进入人工队列。** 复杂冲突、规则不明确和高风险申请不能无限让模型重试。

#### 7. 如何评估审批助手

要分别评估意图识别准确率、字段抽取准确率、缺失字段发现率、规则解释准确率、重复提交拦截率、越权拦截率和一次完成率。

更重要的是观察真实业务指标：用户填写时间是否减少、人工退回率是否下降、审批错误率是否上升、用户是否清楚自己提交了什么。不能只看聊天轮次变少，因为少问几句但提交错误申请并不是成功。

### 继续追问

**Q：模型能不能自动选择审批人？**  
可以帮助解释候选审批链，但最终审批人应由组织和流程配置确定，不能只靠模型猜测。

**Q：审批 API 超时了怎么办？**  
先用幂等键查询原始实例状态，确认没有创建成功后再有限重试，不能盲目重复提交。

**Q：模型判断申请符合条件，可以直接提交吗？**  
不可以。规则和权限必须由后端确定性校验，涉及高风险动作还要用户确认。

**Q：用户说“帮我撤回刚才的审批”怎么办？**  
先确认目标实例、用户身份和撤回条件，展示影响后再执行，并记录审计日志。

### 面试总结

审批助手的核心是“Agent 帮用户把事情说清楚，Workflow 保证事情按规则发生”。模型可以理解意图、收集字段和解释状态，但不能替代权限系统、规则引擎和审批人。

回答时只要把自然语言入口、字段补全、规则校验、用户确认、幂等提交、状态查询和异常转人工讲清楚，就能体现你理解了企业 Agent 的真正边界。

## 02-04 多维表格数据分析 Agent 怎么设计？

### 面试官追问

**面试官：** 如果用户用自然语言询问飞书多维表格里的业务数据，例如“统计本月各区域销售额，并找出风险项目”，你会怎么设计？

**我：** 让大模型理解问题，然后调用多维表格 API 查询数据，最后生成分析结果。

**面试官：** 模型怎么知道字段含义？它生成的筛选条件和聚合逻辑正确吗？用户没有权限看某些记录怎么办？如果数据量很大或问题有歧义怎么办？

这道题考察的是自然语言到数据查询的转换能力。真正的难点不在于让模型生成一段代码，而在于理解表结构、明确统计口径、控制查询权限，并且让最终数字可以复算和追溯。

### 常见错误回答

“把多维表格数据全部交给大模型，让它自己分析并生成图表。”

这样做既浪费上下文，又容易泄露数据。模型可能把“销售额”理解成含税金额或回款金额，把“本月”理解成自然月或近 30 天，也可能在数据没有加载完整时直接给出看似精确的结论。

### 30 秒简答

我会设计成“语义理解 + 查询计划 + 受控数据执行 + 可追溯分析”的 Agent。系统先读取用户有权限访问的表、字段和视图元数据，把自然语言问题转换成结构化查询计划，包括指标、维度、过滤条件、时间范围和排序方式。

查询计划需要经过字段校验、权限校验和口径确认，再由确定性的数据服务执行。模型负责解释结果、发现异常和生成摘要，但所有数字都要来自真实查询结果，并保留查询条件、数据时间和字段来源。问题有歧义时先追问，不要自行选择统计口径。


### 原理拆解

#### 1. 自然语言问题要先变成分析计划

“本月各区域销售情况怎么样”不是一个足够精确的查询。它至少涉及：销售额还是订单数、按签约还是回款统计、区域字段是哪一个、时间按什么字段计算、是否排除取消订单。

因此可以先生成一个中间结构：

```json
{
  "metric": "回款金额",
  "dimension": "区域",
  "time_range": "2026-08-01 至 2026-08-31",
  "filters": ["订单状态=已完成"],
  "sort": "金额降序"
}
```

这个中间结构比让模型直接拼 API 参数更容易校验，也更方便用户确认和问题排查。

#### 2. Schema 不只是字段名，还包括业务语义

多维表格里的字段可能叫“金额”“状态”“负责人”，但模型不知道金额是否含税，状态有哪些枚举值，负责人是姓名还是用户 ID。

元数据层应该提供：

- 字段名称和类型；
- 字段描述和业务口径；
- 枚举值及其含义；
- 计算字段和公式说明；
- 时间字段的定义；
- 表、视图和记录的权限范围；
- 数据更新时间和质量状态。

没有这些信息，模型只是根据字段名猜测，分析结果很容易“语法正确、业务错误”。

#### 3. 查询执行要限制模型的自由度

模型可以提出查询计划，但不应该直接获得任意数据库或任意代码执行权限。更稳妥的方式是提供受控的查询工具，只允许使用已注册的表、字段、过滤器和聚合函数。

执行前至少校验：

```text
表和视图是否允许访问
-> 字段是否真实存在
-> 过滤条件是否符合类型
-> 时间范围是否过大
-> 是否触发敏感数据限制
-> 是否需要用户确认
```

对于大规模数据，系统应该先做服务端聚合、分页或抽样，不要把全部记录直接放进模型上下文。

#### 4. 统计口径不清时应该追问

以下问题不能让模型默默替用户决定：

- “销售额”是合同金额、订单金额还是回款金额？
- “本月”按自然月还是最近 30 天？
- “风险项目”按逾期、毛利下降还是负责人未更新判断？
- 是否包含取消、退款或测试数据？

Agent 可以提出默认口径，但应该把默认值展示出来，让用户确认。对于低风险探索可以先给出假设；对于财务、经营和绩效数据，应先追问清楚再计算。

#### 5. 分析结果要能复算

最终答案不能只有一句“华东区域风险最高”。至少应包括：统计时间、数据范围、使用字段、筛选条件、关键数字和异常判断依据。

可以把结果分成三部分：

```text
数据结果：查询直接计算出的数字
分析结论：模型基于结果归纳的趋势
限制说明：数据更新时间、样本范围和口径假设
```

如果用户追问“这个数字怎么算出来的”，系统应该返回查询计划或可复用的分析链接，而不是重新凭记忆解释一遍。

#### 6. 权限和敏感数据要贯穿查询过程

多维表格可能包含客户联系方式、员工绩效、合同金额和成本数据。用户能看到表格，不代表能看到所有字段和记录。

权限控制要覆盖：

- 用户是否能访问该表或视图；
- 是否有记录级过滤；
- 敏感字段是否需要脱敏；
- 聚合结果是否会反推个人数据；
- 导出和分享是否需要额外确认。

不能先查询全量数据，再让模型删除敏感字段。数据边界要在查询服务层前置执行。

### 企业协作场景

销售负责人问：“统计本月各区域回款金额，并找出连续两周没有更新跟进记录的项目。”

Agent 先确认“本月”是自然月，“回款金额”对应回款字段，“项目未更新”对应最后跟进时间字段。查询服务按用户权限执行聚合，再筛选超过两周未更新的项目，返回结果和数据更新时间。

如果用户要求导出所有项目负责人和客户联系方式，系统需要单独判断字段权限，不能因为前面的统计查询成功就默认允许导出明细。

### 工程方案与取舍

1. **优先建立元数据目录。** 没有字段语义，模型很难稳定分析。
2. **使用中间查询计划。** 先校验计划，再执行真实数据查询。
3. **服务端完成聚合和过滤。** 避免把大量明细数据塞入上下文。
4. **把数字和解释分开。** 数字来自查询服务，模型只负责组织和解释。
5. **敏感字段默认隐藏或脱敏。** 聚合也要防止小样本反推个人信息。
6. **大范围查询要限时和限量。** 超出范围时提示用户缩小条件，而不是无限等待。

#### 7. 如何评估分析 Agent

评测集应覆盖简单查询、组合筛选、时间范围、字段别名、口径歧义、权限限制、空数据和异常数据。重点指标包括查询计划正确率、字段映射准确率、最终数字准确率、权限拦截率、追问合理性和结果可复算率。

如果数字准确但用户经常投诉口径不清，问题可能在交互设计而不在模型。线上要保存脱敏后的查询计划和执行结果，方便复盘错误来源。

### 继续追问

**Q：为什么不直接让模型生成 SQL？**  
直接生成 SQL 自由度太高，容易越权、访问不存在字段或造成高成本查询。可以让模型生成受控的查询计划，再由服务层编译执行。

**Q：数据量太大怎么办？**  
先在数据服务端过滤、聚合和分页，必要时使用缓存或异步任务，不能把全量数据放进上下文。

**Q：模型分析错了，先换更大的模型吗？**  
先检查字段语义、口径、查询计划和真实执行结果。很多问题是数据建模或权限问题，不是模型能力问题。

**Q：用户要求导出敏感数据怎么办？**  
重新做字段级权限和风险确认，必要时脱敏、审批或拒绝，不能沿用普通查询权限。

### 面试总结

多维表格分析 Agent 的核心不是“让模型看表格”，而是把自然语言问题转换成可校验、可执行、可复算的查询计划。

回答时要讲清楚元数据、口径确认、权限过滤、服务端执行、结果引用和异常处理。模型负责理解和解释，数据服务负责计算，权限系统负责边界，这样才能把自然语言分析做成可靠的企业能力。

## 02-05 IM 消息与待办自动化 Agent 怎么设计？

### 面试官追问

**面试官：** 如果让你设计一个基于飞书 IM 的消息和待办自动化 Agent，它能从群聊里识别任务并提醒相关人员，你会怎么做？

**我：** 监听群消息，让大模型识别里面有没有任务，有的话就自动创建待办并通知负责人。

**面试官：** 普通讨论和正式任务怎么区分？负责人没有明确说是谁怎么办？群里一句玩笑会不会变成待办？重复消息怎么处理？私聊和群聊的权限一样吗？

这道题考察的是事件驱动 Agent 的边界。系统不仅要理解消息，还要判断是否应该行动、行动对象是谁、是否需要确认，以及如何避免重复通知和过度自动化。

### 常见错误回答

“把群消息实时丢给模型，只要识别到‘完成’‘跟进’‘安排’这些词，就自动创建任务。”

关键词触发非常容易误报。群聊里有讨论、引用、转发、玩笑和历史任务，不能因为出现一个动作词就代表用户授权了自动执行。消息自动化首先要处理意图置信度、上下文和用户确认。

### 30 秒简答

我会采用“事件接收 + 意图识别 + 待确认草稿 + 确定性执行”的架构。系统通过事件订阅接收授权范围内的消息，先做去重、过滤和上下文拼接，再让模型识别消息是普通讨论、明确任务、提醒请求还是需要人工确认的内容。

对于负责人、截止时间或任务内容不明确的消息，Agent 生成待确认卡片，不直接创建。用户确认后，后端使用幂等键创建待办，并根据通知策略发送消息。整个过程要控制群聊权限、消息隐私、重复事件和通知频率。


### 原理拆解

#### 1. 先区分“看到了消息”和“获得了行动授权”

事件订阅告诉系统某条消息发生了，但不等于用户授权系统执行写操作。比如“这个问题下周再跟进”可能只是讨论，也可能是一个正式任务。

可以把消息意图分成几类：

- 普通信息：只需要记录或忽略；
- 明确任务：内容、负责人和时间都清晰；
- 潜在任务：有动作倾向，但字段不完整；
- 查询请求：需要搜索资料或查询状态；
- 高风险动作：涉及外部通知、数据修改或敏感信息。

只有明确任务或用户确认后的潜在任务，才进入自动创建流程。

#### 2. 消息上下文要有限、相关和可解释

单条消息经常缺少主语和背景，例如“这个周五前搞定”“还是按上次的方案”。Agent 需要读取一定范围的上下文，但不能默认把整个群聊历史都塞进模型。

上下文可以按以下优先级组织：

```text
当前消息
-> 被回复的消息
-> 同一主题的近期消息
-> 明确提到的文档或任务
-> 用户授权可访问的相关历史
```

系统还要保留哪些消息被用于判断，方便用户追问“为什么给我创建了这个任务”。

#### 3. 任务字段抽取不能靠猜

创建待办至少需要标题、负责人和截止时间，实际还可能包括优先级、项目、描述和附件。

例如“@小王 下周把客户方案更新一下”，负责人比较明确，但“下周”需要结合当前日期转成具体时间，还应展示给用户确认。如果消息只说“大家关注一下”，就不应该自动指定负责人和截止日期。

字段状态可以是已确认、待确认、缺失和冲突。模型只能提出候选值，不能把不确定信息当成事实写入任务。

#### 4. 事件处理必须幂等和可恢复

消息事件可能重复投递、乱序到达或因为网络问题重试。每个事件都应该有唯一事件 ID，任务创建也要使用幂等键。

处理链路可以是：

```text
接收事件
-> 校验签名与来源
-> 根据事件 ID 去重
-> 生成意图草稿
-> 等待用户确认
-> 使用幂等键写入待办
-> 记录结果并发送一次通知
```

如果创建接口超时，系统先查询幂等键对应的任务状态，不能因为“没收到响应”就再次创建。

#### 5. 通知自动化要控制频率和范围

一个任务可能同时触发群消息、私聊提醒、截止日期提醒和逾期提醒。如果没有合并策略，Agent 会变成消息轰炸器。

通知策略应明确：

- 谁需要知道；
- 什么时候通知；
- 同一事件最多通知几次；
- 是否允许静默时段；
- 用户能否关闭或调整提醒；
- 群通知和私聊通知分别使用什么内容。

涉及客户、绩效、合同或个人信息时，不能把原始消息直接转发到更大的群里。

#### 6. 人机协同应该放在不确定节点

自动化不是越多越好。置信度高、影响低、字段完整的任务可以自动执行；负责人不明、截止时间模糊、涉及多人或有外部副作用的任务，应该生成确认卡片。

确认卡片要让用户看到：任务标题、负责人、时间、来源消息、通知范围和创建后的影响。用户可以修改字段、确认、拒绝或转交人工。

### 企业协作场景

项目群里有人说：“@小李 请在周五前把接口文档补齐，完成后提醒我。”

系统识别出负责人、截止日期、任务内容和提醒对象，生成待办草稿。小李确认后创建任务，周四进行一次提醒，完成后根据任务状态通知发起人，而不是每次看到“接口文档”都重复生成任务。

如果消息是“大家讨论一下接口文档要不要补齐”，系统只记录为潜在任务，不自动创建。

### 工程方案与取舍

1. **事件订阅和任务执行解耦。** 先持久化事件，再异步处理，避免消息接收接口被模型调用阻塞。
2. **使用规则做第一层过滤。** 机器人未被提及、非目标群、系统消息和重复消息可以先过滤。
3. **模型只处理候选消息。** 减少成本并降低误触发。
4. **低风险自动化，高风险确认。** 创建个人待办和发送私聊提醒可以逐步自动化，群发、外部通知和数据修改需要确认。
5. **幂等、重试和死信队列必须具备。** 事件失败不能静默丢失，也不能无限重试。
6. **给用户提供撤销和关闭入口。** 自动化系统必须允许纠错。

#### 7. 如何评估消息 Agent

重点指标包括任务识别准确率、误触发率、字段抽取准确率、确认转化率、重复任务率、通知送达率、关闭自动化的比例和平均处理延迟。

不要只追求自动创建数量。一个每周创建很多任务但误报严重的系统，会快速失去用户信任。更有价值的是降低漏任务和重复劳动，同时让用户能解释、修改和撤销系统行为。

### 继续追问

**Q：群里出现“@小王跟进一下”可以直接建任务吗？**  
可以识别为候选任务，但要根据上下文和配置决定；信息不完整时应先确认，不能只凭关键词执行。

**Q：事件重复发送怎么办？**  
使用事件 ID 去重，任务写入使用幂等键，失败后先查询状态再重试。

**Q：机器人能读取群里所有历史吗？**  
不能。只读取授权范围内、与当前任务相关的最小上下文，并遵守群和用户权限。

**Q：用户创建错任务怎么办？**  
提供撤销、修改和删除入口，同时保留审计记录；高风险删除操作需要再次确认。

### 面试总结

IM 自动化 Agent 的核心不是“监听消息后自动做事”，而是判断什么时候消息真正代表行动授权。

回答时要把事件去重、上下文范围、意图识别、字段确认、幂等写入、通知策略和人工兜底讲清楚。模型负责理解消息，事件系统负责可靠接收，任务服务负责确定性执行，用户始终保留确认和撤销权。

## 02-06 企业搜索与员工助手怎么设计？

### 面试官追问

**面试官：** 如果让你设计一个面向全体员工的企业搜索与员工助手，它可以回答“谁负责这个项目”“请假流程在哪里”“有没有相关专家”，你会怎么做？

**我：** 把公司的文档、通讯录和流程都接进知识库，让大模型统一回答。

**面试官：** 员工信息、组织关系和文档权限怎么处理？搜索结果和直接生成答案有什么区别？如果多个文档冲突，或者员工问的是一个动作而不是问题怎么办？

这道题考察的是企业级信息入口设计。员工助手不仅要找资料，还要理解组织、权限、流程和当前状态；但它也不能因为“知道答案”就自动替用户修改组织数据或发起流程。

### 常见错误回答

“把所有公司资料做成一个向量库，再让模型根据相似度回答员工问题。”

企业搜索不是简单的语义问答。员工可能想找一份制度、一个负责人、一个流程入口、一个项目状态，也可能只是想知道去哪里办理。不同问题对应不同数据源和答案形式，权限和数据新鲜度也不能被向量相似度解决。

### 30 秒简答

我会把员工助手设计成“统一入口 + 多源搜索 + 权限过滤 + 结果解释”的 Agent。用户从飞书 IM 或搜索入口提出问题后，系统先识别问题类型，再选择文档、知识库、通讯录、多维表格、日历或流程系统等数据源。

搜索结果只允许来自用户有权限访问且状态有效的数据。对于文档问题返回带引用的答案，对于人员和组织问题返回结构化信息，对于流程问题返回办理入口；如果用户希望执行操作，再进入独立的确认和授权流程。Agent 负责路由、追问和综合结果，数据源系统负责真实状态和权限。


### 原理拆解

#### 1. 企业搜索、知识问答和员工助手不是一回事

三者可以共用底层能力，但目标不同：

| 类型 | 用户想得到什么 | 最适合的输出 |
| --- | --- | --- |
| 企业搜索 | 找到相关内容 | 结果列表、摘要和筛选 |
| 知识问答 | 理解一个问题 | 结论、依据和引用 |
| 员工助手 | 完成一个工作 | 信息、入口或后续动作 |

例如“报销制度在哪里”更像搜索，“报销餐费需要什么材料”更像问答，“帮我发起报销”则是一个带写操作的流程任务。

Agent 需要先判断用户目标，不要把所有问题都改写成一段生成式答案。用户明确想要原文时，应该提供文档入口；用户需要决策依据时，才生成总结。

#### 2. 多源路由是员工助手的核心

不同问题应该去不同系统找答案：

```text
制度和方案 -> 文档/知识库
人员和部门 -> 通讯录/组织架构
项目进度 -> 多维表格/项目系统
会议和安排 -> 日历/会议记录
办理流程 -> 审批/任务系统
```

模型可以做意图分类和查询改写，但路由规则要结合数据源能力和权限。比如“这个项目负责人是谁”不应该只在文档里搜索，还要查询结构化项目数据，并注明信息更新时间。

#### 3. 员工信息和文档信息要分别治理

通讯录数据可能包含姓名、部门、职位、联系方式和汇报关系；文档数据可能包含项目方案、客户信息和内部制度。两者的权限规则和更新频率不同。

系统要区分：

- 哪些字段所有员工可见；
- 哪些信息只对同部门或项目成员开放；
- 是否允许返回联系方式；
- 是否可以根据组织关系推断敏感信息；
- 文档的访问权限是否已经过期。

不能因为用户能搜索到某人的姓名，就默认可以获取其全部联系方式和工作安排。

#### 4. 搜索结果要考虑新鲜度和权威性

企业资料经常存在旧制度、草稿、会议讨论和正式发布版本。相似度最高的文档不一定是最权威的文档。

排序可以综合：

- 数据源权威级别；
- 生效和更新时间；
- 用户与内容的关系；
- 查询文本相关性；
- 文档是否已归档；
- 是否有明确版本号。

如果资料冲突，助手应该说明“存在多个版本”，列出各自时间和来源，并优先推荐当前有效版本。涉及人事、财务、合规和安全的问题，不能只依据一条相似文本下结论。

#### 5. 员工助手要回答“下一步怎么办”

员工经常不需要长篇解释，而是需要明确入口：去哪个文档、找哪个部门、填写什么申请、还缺什么材料。

回答可以分成：

```text
直接答案
-> 官方依据或负责人
-> 办理入口
-> 所需材料
-> 如果仍不确定，应该联系谁
```

如果用户说“帮我申请”，系统再进入审批助手或任务助手，而不是在搜索回答中直接写入业务数据。不同能力之间要通过清晰的工具和确认边界连接起来。

#### 6. 找人和找知识都要防止过度推断

当用户问“谁最懂这个问题”时，系统可以根据公开的项目角色、文档作者和已授权的组织信息推荐候选人，但不能把聊天频率直接当成专业能力，也不能泄露个人评价和私人信息。

推荐结果要说明依据和局限，例如“根据最近维护过相关文档的项目成员推荐”，而不是说“这个人是公司最权威的专家”。

### 企业协作场景

新员工在飞书里问：“我想申请差旅报销，需要什么材料，项目负责人是谁？”

员工助手先从正式制度文档中找到材料要求，再查询该员工所在项目的负责人信息，分别标注来源和更新时间。最后返回报销流程入口。如果用户继续说“帮我填申请”，系统把任务转给审批助手，重新收集金额、时间和附件，并要求提交前确认。

### 工程方案与取舍

1. **统一入口，能力分流。** 不同问题进入不同数据源和工具。
2. **搜索和生成分开。** 用户要原文就提供原文入口，需要理解时再生成摘要。
3. **权限前置，结果带状态。** 不能让模型决定是否可以展示。
4. **建立数据源权威级别。** 正式制度、草稿和群聊记录不能等权处理。
5. **对人员信息做最小化返回。** 只返回完成任务所需的字段。
6. **动作能力单独确认。** 查询结果不能自动变成写操作。

#### 7. 如何评估员工助手

评测要覆盖搜索命中率、路由正确率、答案引用正确率、人员信息准确率、数据新鲜度、权限拦截率、无答案拒答率和用户一次解决率。

还要评估用户是否真的减少了找人、找文档和找流程的时间。线上可以分析用户在回答后是否继续追问、是否点击官方入口、是否转人工，以及哪些问题长期没有可靠答案，这些都能帮助补齐企业知识体系。

### 继续追问

**Q：企业搜索为什么一定要接大模型？**  
不是所有搜索都需要大模型。关键词搜索更适合找精确名称，大模型适合意图理解、查询改写、跨来源总结和自然语言交互。

**Q：如果两个制度文档冲突怎么办？**  
按权威级别和生效时间排序，向用户展示冲突和来源，必要时转给制度负责人确认。

**Q：用户问某个同事的联系方式能直接给吗？**  
根据字段权限和业务必要性决定，默认最小化返回，不能因为姓名可见就泄露全部联系方式。

**Q：员工助手能直接帮用户办理业务吗？**  
可以通过受控工具进入流程，但必须重新校验身份、权限、字段和确认，不应从搜索结果直接执行写操作。

### 面试总结

企业搜索与员工助手的核心，是把“找资料、找人、找流程和做事情”统一到一个入口，但不把所有问题都交给一个模型自由回答。

回答时要讲清楚问题路由、多源检索、权限过滤、权威性和新鲜度、引用回答，以及搜索到行动之间的确认边界。一个成熟的员工助手应该让员工更快找到可信信息，同时让企业掌握数据、权限和动作风险。

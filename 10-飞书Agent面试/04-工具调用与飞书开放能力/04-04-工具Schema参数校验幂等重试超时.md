# 04-04 工具 Schema、参数校验、幂等、重试与超时

## 面试官追问

**面试官：** Agent 调用工具时，怎样保证参数正确和服务可靠？

**我：** 用 JSON Schema 约束参数，失败就重试几次。

**面试官：** 参数格式正确但业务上不合法怎么办？创建任务重试会不会创建两次？

## 常见错误回答

“Schema 校验通过就可以直接执行，所有错误都统一重试。”

Schema 只能描述结构，不能覆盖权限、状态、额度和幂等语义；统一重试会把业务拒绝变成重复写入。

## 30 秒简答

我会把校验分成 Schema 校验、语义校验、权限校验和业务状态校验。工具定义中明确必填字段、枚举、长度、格式和风险等级，运行时再校验资源归属、当前状态和用户权限。

读操作可以对临时网络错误有限重试，写操作必须携带幂等键并区分“已成功但响应丢失”。每个工具设置连接超时、执行超时和总预算，超时后查询结果或进入人工处理，不能让 Agent 无限重试。

## 原理拆解

### 1. 四层参数校验

Schema 校验类型和必填字段；语义校验日期、数量、枚举和引用关系；权限校验用户能否操作目标资源；业务校验当前状态、额度、审批条件和并发版本。只有全部通过才进入执行。

### 2. 幂等键要贯穿写链路

客户端或 Agent Runtime 生成稳定的 idempotency_key，服务端保存请求指纹、状态和结果。重复请求返回第一次结果，参数指纹变化则拒绝，防止同一个键被滥用。

### 3. 错误要区分可重试性

网络断开、服务暂时不可用和限流通常可重试；参数错误、权限拒绝、资源不存在和业务规则拒绝不可自动重试；未知错误先查询服务端状态，避免把“响应丢失”误判为未执行。

## 企业协作场景

用户要求“给每个项目负责人创建待办”。Agent 先确认项目列表和负责人，批量生成幂等键，逐项执行。某一项权限不足时只失败该项，并向用户说明，不重复创建已经成功的任务。

## 工程方案与取舍

1. 超时分层设置，并给 Agent Loop 设置更短的总预算。
2. 重试使用指数退避和抖动，避免雪崩。
3. 记录请求指纹、幂等键、状态转换和下游 request_id。
4. 对批量操作支持部分成功、重试单项和人工重放。

## 继续追问

**Q：幂等键只放在 Prompt 里可以吗？** 不可以，必须由运行时和服务端生成、保存和校验。

**Q：超时后能直接重试写操作吗？** 先查询服务端状态或使用幂等键确认结果，再决定是否重试。

## 面试总结

可靠工具调用依赖“结构校验 + 业务校验 + 幂等 + 分类重试 + 分层超时”。模型可以重新规划，但不能绕过这些运行时约束。

## 深入展开：可靠性设计的几个容易漏掉的点

### 1. 连接超时和执行超时分开

连接超时表示还没有建立到下游服务的连接，执行超时表示请求已经送达但服务迟迟没有返回。二者的重试风险不同：连接失败通常可以重试，执行超时要先查询幂等状态，避免服务已经成功而客户端没有收到响应。

### 2. 幂等键要能追踪业务意图

对于“创建任务”或“提交审批”，幂等键可以由租户、用户、任务 ID、动作类型和参数摘要生成。服务端保存第一次请求的结果和参数指纹，重复请求返回同一结果；如果同一键对应不同参数，应拒绝而不是覆盖。

### 3. 批量操作采用部分成功模型

批量创建或更新时，不要把所有对象放进一次无法恢复的调用。每个对象有独立幂等键和结果状态，返回成功、失败、可重试和待确认列表。Agent 可以向用户说明哪些已经完成，避免用一句“批量操作失败”掩盖部分成功。

### 4. 重试要有预算

单个工具设置最大次数，整个 Agent 任务还要设置总重试预算和总耗时。退避策略加入随机抖动，避免大量 Agent 同时重试造成下游雪崩。超过预算后转为人工重放或返回明确错误。

## 从错误分类到恢复策略

参数错误通常不应重试，而是把缺失字段和允许值返回给模型或用户；权限错误需要提示授权或转人工；限流和临时网络错误可以在预算内退避重试；源系统已接受但响应超时，要先用幂等键查询结果，不能直接再次创建；业务规则拒绝则必须停止，不能让模型换一种说法绕过规则。不同错误对应不同处理路径，统一重试会放大事故。

批量工具还要返回逐项结果：成功记录、失败记录、可重试记录和未知状态记录。任务重试时只处理未知或明确可重试的部分，避免把已成功的数据再次写入。超时要区分连接超时、服务端执行超时和客户端等待超时，并设置总预算，保证 Agent Loop 不会因为一个慢工具无限等待。

Schema 设计也要服务于可恢复性。参数名称要表达业务含义，枚举值要限制范围，危险字段要拆开，默认值不能掩盖用户没有提供的信息。所有调用都带 trace_id、idempotency_key 和 schema_version，后续才能从日志还原一次调用的意图、校验结果和最终状态。

## 面试追问补充：重试为什么可能造成事故

读取接口通常可以安全重试，但创建、发送、审批和删除不一定安全。客户端超时并不代表服务端没有执行，重试前应查询幂等键或业务状态；如果源系统不支持幂等，就需要在本地建立请求表、状态表和补偿流程。重试次数不是越多越好，应按错误类型和剩余总预算决定。

对于批量任务，失败结果要让用户看懂：哪些已经成功、哪些等待确认、哪些可以重试、哪些被业务规则拒绝。系统不能把部分成功包装成整体成功，也不能让模型把拒绝原因改写成另一个参数继续提交。可靠工具的核心是状态透明和边界明确。

## 面试追问补充：Schema 还要考虑演进

Schema 不是一次写完就不变。新增可选字段通常兼容，修改字段含义、枚举值或默认行为则需要新版本；旧任务继续使用旧 Schema，新的调用使用新版本，服务端可以同时兼容一段时间。历史 Trace 要能找到当时的 Schema，才能解释旧请求为什么失败。

参数校验错误应返回字段级提示和允许范围，避免模型不断猜测。对危险参数采用白名单和服务器端映射，用户输入的资源名先解析成内部 ID，再执行。这样即使模型产生格式正确的恶意参数，工具服务仍能阻止越权和错误写入。

## 面试进阶回答

### 工具层的可测试性

工具层要把参数校验、权限校验、实际调用和结果标准化拆开。单元测试覆盖缺字段、类型错误、越界值和重复请求；集成测试覆盖接口超时、部分成功和事件延迟；回放测试则使用真实 Trace 验证同一个工具版本能否稳定处理历史请求。模型只负责提出参数，工具服务必须独立拒绝非法请求，并返回可供上层处理的错误类型。

“我会把校验分成结构、语义、权限和业务状态四层，重试只针对可恢复错误。读请求可以有限重试，写请求必须使用服务端幂等键；超时后先查状态再决定动作。工具返回结构化错误，Agent Runtime 按错误类型选择重试、追问或人工接管。”

## 一个完整的错误分类表

| 错误 | 是否自动重试 | 处理方式 |
| --- | --- | --- |
| 参数类型或必填字段错误 | 否 | 让模型修正或向用户追问 |
| 用户无权限 | 否 | 说明权限不足，不绕过策略 |
| 资源状态冲突 | 通常否 | 重新读取状态后请求确认 |
| 网络断开或服务暂时不可用 | 有限重试 | 指数退避并记录次数 |
| 请求已送达但响应超时 | 先查状态 | 使用幂等键确认结果 |
| 下游业务拒绝 | 否 | 返回业务原因或人工处理 |

这张表体现的是工程判断：重试不是越多越好，关键是知道系统当前处于什么状态。

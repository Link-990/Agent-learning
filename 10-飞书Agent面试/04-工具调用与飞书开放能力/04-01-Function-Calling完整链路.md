# 04-01 Function Calling 的完整链路是什么？

## 面试官追问

**面试官：** 大模型是如何调用一个飞书工具的？模型返回函数名就算执行完成了吗？

**我：** 模型输出工具名称和参数，系统调用接口后把结果返回给模型。

**面试官：** Schema、参数校验、权限、失败重试和最终回复分别由谁负责？

## 常见错误回答

“把所有 API 描述放进 Prompt，模型会自动调用并保证参数正确。”

模型只能提出调用意图，不能代替运行时执行、鉴权和业务校验。Function Calling 是协议链路，不是安全边界。

## 30 秒简答

完整链路是：定义工具 Schema，模型根据上下文返回结构化 tool call，运行时校验工具名和参数，进行身份与权限检查，再调用实际服务；服务结果经过脱敏、截断和状态归一后回传模型，模型继续判断是否需要下一步，最终由应用生成回复。

工具调用要有超时、重试、幂等、审计和停止条件。模型输出的参数永远是不可信输入，所有写操作要经过业务服务二次校验，必要时等待用户确认。

## 原理拆解

### 1. 工具描述与执行解耦

Schema 描述名称、用途、参数类型和约束，供模型生成调用意图；工具注册表维护真实 endpoint、权限、超时、风险等级和执行适配器。模型看不到密钥和内部地址。

### 2. 运行时是可信边界

收到 tool call 后依次进行工具白名单、JSON Schema、业务规则、用户身份、租户范围和风险级别校验。校验通过后才调用 API，结果不能直接把内部错误、令牌或敏感字段回传给模型。

### 3. 结果回传要保留状态

工具结果应包含 success、error_code、retryable、request_id、data 和 next_action_hint 等结构化字段。模型可以根据结果继续规划，但不能把 `retryable=false` 的业务拒绝改写成重试。

## 企业协作场景

用户说“帮我把会议纪要发给项目群”。Agent 先查找纪要、确认目标群和收件范围，生成发送草稿；真正发送前展示内容和影响范围，用户确认后才调用消息发送工具。

## 工程方案与取舍

1. 工具按只读、低风险写入、高风险写入分级。
2. 每次调用记录 trace_id、tool_name、参数摘要、耗时、结果码和操作者。
3. 只对网络抖动等临时错误有限重试，参数和权限错误直接返回可修复提示。
4. 用最大轮数、总耗时和预算限制 Agent Loop，防止工具调用失控。

## 继续追问

**Q：模型能直接调用飞书 API 吗？** 不能，模型只能生成意图，运行时通过受控工具适配器调用。

**Q：工具结果要不要全部返回模型？** 不要，按最小必要原则脱敏、截断和结构化。

## 面试总结

Function Calling 的核心是“模型提出调用，运行时负责验证和执行”。Schema 解决可表达性，运行时解决安全和可靠性，Agent Loop 负责根据结果决定是否继续。

## 深入展开：一次调用如何被安全地执行

### 1. 工具注册表比工具描述更重要

面向模型的描述只需要说明工具用途和参数，内部注册表还要保存工具版本、真实服务、所需 scope、允许的租户、风险等级、超时、重试策略和结果脱敏规则。模型只能看到经过筛选的工具集合，不能发现所有后台接口。

### 2. 参数校验要结合用户上下文

例如模型生成 `document_id` 和 `recipient_id`，Schema 可以验证它们是字符串，但不能判断用户是否有权限读取文档、是否能向该群发消息。运行时需要把用户身份、租户、授权范围和工具参数一起交给策略服务判断。

### 3. 工具结果要防止循环失控

结果回传时包含状态码、是否可重试和下一步建议，模型不应看到无限长的原始响应。Runtime 设置最大轮数、总耗时、Token 预算和相同工具重复调用次数；当达到上限时返回部分结果、请求用户确认或转人工。

### 4. 端到端例子

用户说“找出本周延期项目并给负责人建待办”。Agent 先调用文档和表格查询工具，再让模型整理候选；创建待办前，系统重新校验负责人、截止日期和任务内容，生成幂等键并展示草稿。任何一个调用成功都不会自动代表整个任务成功，最终状态由任务编排器确认。

## 工具调用的状态机和可观测性

一个完整的 Function Calling 请求至少有“已规划、待校验、执行中、成功、可重试失败、不可重试失败、等待确认、已取消”这些状态。模型输出工具意图后，运行时先创建调用记录，再做 Schema、权限和额度校验；校验通过才进入执行。这样即使进程重启，也能根据调用记录判断是否需要恢复、查询结果或人工接管，而不是重新让模型猜一次。

工具结果不要只返回一段自然语言。建议同时返回 success、data、error_code、retryable、source_id、request_id 和 next_action。模型可以根据 next_action 继续规划，但运行时要限制最大轮数、单工具预算和总耗时。对写操作还要把参数摘要、确认令牌和实际执行结果写入审计日志，便于解释“模型想做什么”和“系统实际做了什么”的差异。

评测时可固定用户目标和工具集合，检查模型是否选对工具、参数是否完整、错误后是否选择正确分支、成功后是否停止。真正上线的 Function Calling 不是“能输出 JSON”就完成，而是模型意图、可信运行时、可恢复执行和审计记录共同构成闭环。

## 面试追问补充：什么时候不该调用工具

如果用户的问题可以直接依据当前上下文回答，就不必为了体现 Agent 能力而调用工具。调用前应先判断信息是否新鲜、是否需要授权、是否会产生副作用以及是否值得承担额外延迟。查询天气、读取实时审批状态和创建任务的决策不同，工具选择本身也是风险判断的一部分。

工具返回空结果时，系统应区分“没有数据”“没有权限”“查询条件过窄”和“服务异常”。只有第一类可能需要改写查询，其余情况应解释原因或转人工。把这些分支写进运行时，才能避免模型在没有证据时不断换参数重试。

## 面试追问补充：工具结果如何影响下一步

运行时应把工具结果分成成功事实、空结果、可恢复失败、权限拒绝和未知状态。成功事实可以进入上下文，空结果可能触发一次受控改写，可恢复失败进入有限重试，权限拒绝转为说明或人工，未知状态先查询幂等结果。模型不能把所有结果都当成普通文本自由解释。

任务完成后还要检查终止条件：目标是否完成、是否已经获得足够证据、是否达到调用轮数或时间预算、是否需要用户确认。明确停止比让模型一直“再查一下”更重要。

## 面试进阶回答

“Function Calling 只是模型和运行时之间的结构化消息格式。真正的生产链路还包括工具白名单、Schema、业务校验、权限策略、超时重试、幂等、结果脱敏和 Agent Loop 停止条件。模型可以根据工具结果调整路线，但永远不能绕过运行时。”

### 一个常见误区

工具调用成功只表示下游接口接受了请求，不一定表示业务已经完成。例如创建任务后还要确认任务 ID、状态和权限；发送消息后还要确认飞书返回的消息状态。Runtime 应把“请求已发送”“业务已成功”“等待异步结果”区分开，避免模型提前向用户宣布成功。

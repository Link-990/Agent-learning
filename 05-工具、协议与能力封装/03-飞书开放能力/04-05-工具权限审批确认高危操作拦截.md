# 04-05 工具权限、审批确认与高危操作拦截

## 面试官追问

**面试官：** Agent 可以调用飞书发送消息、修改表格或提交审批吗？哪些动作必须拦截？

**我：** 只要用户授权了，就可以让 Agent 执行。

**面试官：** 用户授权是一次性的还是针对每次动作？如何防止模型扩大操作范围？

## 常见错误回答

“在系统 Prompt 里写清楚不能做危险操作。”

高风险控制不能靠 Prompt。权限、审批、确认和额度必须由模型外部的策略引擎和工具服务执行。

## 30 秒简答

我会按工具和参数给动作分级：只读查询可自动执行，低风险写操作可以在用户授权范围内执行，发送外部消息、批量修改、提交审批、删除和权限变更属于高风险动作，需要展示目标、内容、影响范围和操作者后让用户确认，必要时走二次审批。

授权采用最小权限、短时有效和资源范围约束，运行时对每次调用重新鉴权。模型不能自行修改收件人、金额、范围或审批人，所有高危动作都要可撤销、可审计或进入人工接管。

## 原理拆解

### 1. 风险来自动作和上下文

同一个“发送消息”工具，发给自己和发给全员风险不同；修改一条草稿和批量修改生产数据风险不同。因此风险策略要结合工具、资源、对象数量、数据敏感级别和外部影响计算。

### 2. 授权要绑定意图范围

用户说“把这份会议纪要发给项目组”，授权范围应绑定具体文档、群组、内容摘要和有效时间，而不是给 Agent 一个永久的消息发送权限。参数发生实质变化时应重新确认。

### 3. 确认页要让用户看懂影响

确认卡片至少展示动作、对象、收件人、关键字段、风险提示、预计影响和撤销方式。不能只显示“是否继续”，否则用户无法知道确认的是什么。

## 企业协作场景

Agent 发现一条群消息需要转成待办并@负责人。创建草稿可以自动完成，但发送群消息前要显示内容和目标群；如果涉及全员群或敏感附件，系统升级为审批或禁止执行。

## 工程方案与取舍

1. 工具注册表中保存风险等级和所需 scope，策略引擎集中判断。
2. 高风险动作使用短期 confirmation_token，确认内容与最终参数绑定。
3. 对批量操作设置数量、金额和频率上限，超限转人工。
4. 审计记录既包含成功动作，也包含被拦截和用户取消的动作。

## 继续追问

**Q：用户明确说“全部删除”还要确认吗？** 对不可逆或影响范围大的动作仍要二次确认，确认应展示具体对象和数量。

**Q：如何防止 Prompt Injection 诱导高危工具？** 工具层不信任模型指令，始终执行权限、风险和用户确认策略。

## 面试总结

高危工具的控制原则是最小权限、明确范围、逐次确认、参数绑定、可审计和人工接管。用户授权不等于模型可以无限扩大操作范围。

## 深入展开：确认机制如何避免“确认了 A，执行了 B”

### 1. 确认对象必须结构化

确认卡片中的文档、收件人、金额、记录数量、附件和操作类型都要生成结构化摘要，并计算参数指纹。用户确认后，服务端只接受与指纹一致的工具请求；如果模型在确认后改变了收件人或扩大了范围，必须重新确认。

### 2. 授权和确认是两个概念

授权说明用户或管理员允许某类资源访问，确认说明用户此刻明确同意某一个具体动作。即使用户拥有发送消息的权限，批量外发敏感附件仍然需要逐次确认或审批。两者不能用一个永久 Token 代替。

### 3. 高风险动作要可补偿

删除、外发、批量修改和审批提交无法完全回滚时，要在执行前展示影响范围，并提供撤回、补偿或人工处理路径。对不可逆动作可以先生成草稿或导出清单，等待用户确认后再执行。

### 4. 异常路径也要拦截

确认等待期间权限可能变化、资源可能被删除、任务可能超时。执行前需要重新查询状态和重新鉴权；如果不满足条件，应让确认失效并提示用户，而不是强行执行旧请求。

## 如何划分风险等级

可以把工具按读写、影响范围、可逆性和外部影响分级。读取公开制度属于低风险；读取敏感人事或财务资料属于中风险；创建任务、发送群消息、修改表格属于需要确认的写操作；删除数据、审批通过、批量外发和权限变更属于高风险，必须经过更强的授权或人工审批。风险等级应由运行时计算，不能完全相信模型传入的 level 字段。

确认卡片要把最终参数的摘要展示给用户，确认令牌绑定资源版本、收件人、金额、内容哈希和有效期。执行时重新检查用户身份、工具权限、资源是否变化以及是否超过额度。如果执行接口支持撤销，应把撤销入口和期限一起返回；不可逆动作则要在确认前明确提示影响范围。

防护还要覆盖间接调用。例如模型先创建草稿，再让另一个工具自动发送，第二个工具仍应重新判断风险，不能因为上一步已经“确认”就放行。安全边界必须存在于每个高风险工具的服务端，而不是只存在于卡片按钮或 Prompt 中。

## 面试追问补充：写操作前后都要校验

确认前校验的是用户想做什么，执行前校验的是当前是否仍然允许做。两次校验之间可能发生权限撤销、资源版本变化、收件人变化或额度耗尽，因此确认令牌必须绑定参数摘要和资源版本。执行结果还要返回实际影响对象，若与确认对象不一致，应标记异常并暂停后续动作。

对于不可逆动作，优先提供草稿、预览、定向发送和小批量试运行；对于可逆动作，提供撤销期限和补偿接口。高风险操作即使来自可信用户，也要保留审计和人工审批，因为错误可能来自模型解析、数据变化或工具实现，而不只是恶意用户。

## 面试追问补充：确认流程如何防社工和误触

确认卡片不应只显示“确认执行”，还要显示真实对象、目标范围、关键字段和风险提示。对批量发送、删除和权限变更增加二次确认或输入指定短语；对异常时间、异常设备或异常金额可以提高人工审批等级。确认本身也要写入审计，便于事后证明用户看到了什么。

如果用户点击确认后参数发生变化，旧令牌立即失效并重新展示差异。卡片过期、重复点击和多人同时操作时，以服务端状态为准。人机协同的目标是降低误操作概率，不是让确认按钮成为自动放行开关。

## 面试进阶回答

### 确认不是一句“是否继续”

高风险确认应展示动作对象、影响范围、关键字段、执行人、预计结果和撤销方式。确认令牌要绑定用户、工具、参数摘要和有效期，不能让用户确认一次后无限复用。执行前还要重新检查权限和资源版本，因为用户点击确认到真正执行之间，权限或数据可能已经发生变化。

“我会把动作风险和具体参数一起评估。低风险查询自动执行，高风险写入先生成草稿，确认卡片展示对象、收件人和影响范围，并用一次性 token 绑定参数指纹。真正执行前重新鉴权和查状态，所有成功、拒绝、取消和过期都写入审计。”

### 设计确认卡片时的最低字段

至少展示动作名称、目标资源、收件人或影响对象、关键字段、附件、数量、风险提示、确认有效期和取消入口。确认按钮背后应携带任务 ID、参数摘要和策略版本；卡片过期、权限改变或资源状态改变后，原确认自动失效。这样用户确认的是清楚的具体动作，而不是一句模糊的“继续”。

# LangGraph 学习大纲

> 目标：从零开始，系统掌握 LangGraph——一个用于构建有状态、可编排 AI Agent 的图结构框架。
> 学习顺序经过精心设计，每一章都建立在前一章的基础上。

---

## 第一章：LangGraph 是什么，为什么要学它

- 1.1 一句话理解 LangGraph：用"图"来编排 AI Agent 的工作流
- 1.2 从 LangChain 到 LangGraph：为什么 Agent 开发需要图结构？
- 1.3 LangGraph 解决了什么问题？（状态管理、循环、人工介入、持久化）
- 1.4 LangGraph 在整个 AI Agent 生态中的定位
- 1.5 安装与环境准备

## 第二章：核心概念——State、Node、Edge

- 2.1 State（状态）：Agent 的"记忆"，所有节点共享的数据结构
- 2.2 Node（节点）：执行具体逻辑的函数——可以是 LLM 调用，也可以是普通代码
- 2.3 Edge（边）：节点之间的连接，决定"下一步去哪"
- 2.4 一个最简图：Hello LangGraph（完整代码 + 运行）
- 2.5 用大白话理解：State 是黑板，Node 是干活的人，Edge 是流程箭头

## 第三章：StateGraph API——经典构建方式

- 3.1 StateGraph 类详解：如何定义和初始化一个图
- 3.2 用 TypedDict + Annotated 定义自定义 State
- 3.3 MessagesState：LangGraph 内置的消息状态（做对话 Agent 必用）
- 3.4 add_node() 与 add_edge()：组装你的第一个工作流
- 3.5 START 与 END：特殊节点的含义与用法
- 3.6 条件路由（Conditional Edges）：让 Agent 自己决定下一步做什么
- 3.7 实战：构建一个带工具调用的 ReAct Agent

## 第四章：Functional API——用装饰器写 Agent

- 4.1 为什么需要 Functional API？（更 Pythonic，更少样板代码）
- 4.2 @entrypoint：把普通函数变成工作流入口
- 4.3 @task：定义独立的工作单元
- 4.4 可注入参数：previous、store、writer、config 怎么用
- 4.5 Functional API vs StateGraph API：什么时候用哪个？
- 4.6 实战：用 Functional API 重写第三章的 ReAct Agent

## 第五章：持久化系统——让 Agent 记住事情

- 5.1 为什么需要持久化？（对话记忆、故障恢复、审计追踪）
- 5.2 Checkpointer（检查点）：线程级的短期记忆
  - 5.2.1 MemorySaver / InMemorySaver：开发调试用
  - 5.2.2 SqliteSaver / PostgresSaver：生产环境用
  - 5.2.3 thread_id 的概念与使用
- 5.3 Store（存储）：跨线程的长期记忆
  - 5.3.1 InMemoryStore 与语义搜索
  - 5.3.2 Namespace 设计：如何组织你的记忆数据
  - 5.3.3 Store 与 Checkpointer 的关系和协作
- 5.4 实战：给 Agent 加上跨会话记忆

## 第六章：Human-in-the-Loop——人工介入机制

- 6.1 为什么需要人工介入？（审批、纠错、安全兜底）
- 6.2 interrupt()：暂停 Agent 执行
- 6.3 Command(resume=...)：恢复 Agent 执行
- 6.4 stream_events + interrupt 的循环模式
- 6.5 实战：构建一个"花钱需要审批"的 Agent

## 第七章：Streaming——流式输出与实时交互

- 7.1 为什么 Agent 需要流式输出？
- 7.2 stream_events() 与 v3 协议
- 7.3 消息流、Token 流、中断事件——三种流类型
- 7.4 前端集成模式：怎么把 Agent 输出实时展示给用户
- 7.5 实战：带进度条和实时日志的 Agent

## 第八章：多 Agent 系统——让多个 Agent 协作

- 8.1 为什么需要多 Agent？（职责分离、专业分工）
- 8.2 Supervisor 模式：一个"领导"分配任务给"下属"
- 8.3 Swarm / Handoff 模式：Agent 之间自主交接
- 8.4 层级模式：多层嵌套的 Agent 组织
- 8.5 子图（Subgraphs）：把复杂工作流拆成可复用的子模块
- 8.6 实战：构建一个"研究员 + 写手 + 审核员"的三人协作系统

# 4.1 Functional API 是什么？

Functional API 是 LangGraph 在 v1.0+ 推出的一种新的构建方式。它的核心理念是：**用普通 Python 函数 + 装饰器，来定义 Agent 工作流**。

不需要显式创建图、添加节点、添加边——你只需要写函数，LangGraph 会自动把它们编译成图。

---

## 一个最简单的例子

### 用 StateGraph API 写

```python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class State(TypedDict):
    value: int

def add_10(state):
    return {"value": state["value"] + 10}

def multiply_2(state):
    return {"value": state["value"] * 2}

graph = StateGraph(State)
graph.add_node("add", add_10)
graph.add_node("multiply", multiply_2)
graph.add_edge(START, "add")
graph.add_edge("add", "multiply")
graph.add_edge("multiply", END)

app = graph.compile()
result = app.invoke({"value": 5})
print(result)  # {"value": 30}
```

### 用 Functional API 写

```python
from langgraph.func import entrypoint

@entrypoint
def workflow(value: int) -> int:
    value = value + 10
    value = value * 2
    return value

result = workflow(5)
print(result)  # 30
```

看到区别了吗？
- 不需要定义 State
- 不需要创建 graph
- 不需要 add_node、add_edge
- 就像写普通函数一样

---

## Functional API 的核心组件

### 1. @entrypoint 装饰器

把一个函数变成"工作流入口"。

```python
from langgraph.func import entrypoint

@entrypoint
def my_workflow(input: str) -> str:
    # 工作流逻辑
    return result
```

### 2. @task 装饰器

定义一个"可以异步执行的任务"。

```python
from langgraph.func import task

@task
def my_task(input: str) -> str:
    # 任务逻辑
    return result
```

### 3. 可注入参数

在函数里，可以访问一些特殊的参数：
- `previous`：上一步的结果
- `store`：长期记忆（Store 系统）
- `writer`：流式输出
- `config`：运行时配置

---

## Functional API 的工作原理

虽然你写的是普通函数，但 LangGraph 会：

1. **解析你的函数**：看你调用了哪些 `@task`，有哪些控制流（if、while）
2. **编译成图**：自动生成节点和边
3. **支持中断/恢复**：即使是普通函数，也能暂停和恢复（如果配置了 checkpointer）
4. **支持流式输出**：可以实时输出中间结果

底层还是图——只是你不需要显式定义它。

---

## Functional API vs StateGraph API

### 相同点

- 都支持 checkpointer（持久化）
- 都支持 interrupt（人工介入）
- 都支持 streaming（流式输出）
- 都支持 LangSmith 追踪

### 不同点

| 特性 | StateGraph API | Functional API |
|------|---------------|----------------|
| 代码风格 | 显式定义图、节点、边 | 写普通函数 |
| 学习曲线 | 需要理解图的概念 | 更直观，像写普通代码 |
| 灵活性 | 非常灵活，任意拓扑 | 受限于 Python 控制流 |
| 可视化 | 容易画出图结构 | 图结构是自动生成的 |
| 适合场景 | 复杂工作流、动态路由 | 简单到中等复杂度 |
| 代码行数 | 较多 | 较少 |

---

## 什么时候用 Functional API？

### 适合的场景

1. **工作流逻辑简单**
   - 线性流程：A → B → C
   - 简单分支：if-else
   - 简单循环：for、while

2. **快速原型开发**
   - 想快速验证想法
   - 不需要精细控制每个节点

3. **团队熟悉函数式编程**
   - 习惯写纯函数
   - 不喜欢"图"的抽象

### 不适合的场景

1. **复杂的动态路由**
   - 需要根据 LLM 输出动态决定下一步
   - 多个工具并行调用

2. **需要可视化图结构**
   - 想画出清晰的流程图
   - 需要给非技术人员展示

3. **需要精细控制**
   - 每个节点的超时
   - 节点级别的错误处理

## 一个稍微复杂的例子

### 需求

写一个工作流：
1. 用户输入一个主题
2. LLM 写一篇文章
3. 询问用户是否满意
4. 如果满意 → 结束
5. 如果不满意 → 让 LLM 重写

### 用 Functional API 实现

```python
from langgraph.func import entrypoint, interrupt

@entrypoint
def essay_workflow(topic: str) -> str:
    # 1. LLM 写文章
    essay = write_essay(topic)
    
    # 2. 询问用户（interrupt 会暂停执行）
    is_approved = interrupt({"essay": essay, "question": "满意吗？"})
    
    # 3. 根据用户反馈决定
    if is_approved:
        return essay
    else:
        # 重写
        essay = write_essay(f"{topic}（请改进）")
        return essay

def write_essay(topic: str) -> str:
    # 这里调用 LLM（省略）
    return f"关于 {topic} 的文章..."
```

看，整个逻辑用普通的 Python 代码就表达清楚了！

## Functional API 的限制

虽然 Functional API 很简洁，但它有一些限制：

### 1. 不支持任意的循环回边

StateGraph 可以：

```python
graph.add_edge("llm", "tools")
graph.add_edge("tools", "llm")  # 回到 llm，形成循环
```

Functional API 的循环必须是 Python 的控制流：

```python
@entrypoint
def workflow():
    while need_more:
        result = llm()
        if result.done:
            break
    return result
```

### 2. 不支持动态并行

StateGraph 可以动态地从一个节点出多条边。

Functional API 的并行必须是"静态的"（在代码里能看出来）。

### 3. 调试稍微困难

StateGraph 可以用 `stream()` 看每个节点的执行。

Functional API 的中间步骤没有明确的"节点名"。

---

## 小结

Functional API 是 LangGraph 提供的一种更简洁的构建方式：

- **核心思想**：用普通函数 + 装饰器，自动编译成图
- **优点**：代码简洁、直观、学习曲线平缓
- **缺点**：灵活性不如 StateGraph，不适合复杂工作流
- **适合场景**：简单到中等复杂度的工作流、快速原型

# 1.2 从 LangChain 到 LangGraph：为什么 Agent 开发需要图结构？

在讲 LangGraph 之前，我们得先聊聊 LangChain——因为 LangGraph 就是 LangChain 团队开发的，专门用来解决 LangChain 在构建复杂 Agent 时遇到的问题。

---

## LangChain 的局限：线性思维 vs Agent 的非线性需求

### LangChain 的设计哲学

LangChain 最早的设计理念是"链式调用"（Chain）——把多个组件像流水线一样串起来：

```python
# LangChain 的经典 LCEL 写法
chain = prompt | llm | output_parser
result = chain.invoke({"input": "你好"})
```

这种写法很直观：**从左到右，一步一步执行**。

但问题来了——AI Agent 的工作流往往不是线性的。

---

### Agent 的真实工作流：循环、分支、回退

一个真实的 Agent 工作流是这样的：

```
1. 用户问："北京今天天气怎么样？"
2. LLM 判断：我需要调用天气工具
3. 调用天气 API，返回："晴天，25°C"
4. 把结果喂给 LLM，LLM 生成回复："北京今天晴天，25°C"
5. 返回给用户
```

看起来简单？再看一个复杂点的：

```
1. 用户问："帮我分析一下最近三个月的销售数据"
2. LLM 判断：我需要先查数据库
3. 调用数据库，返回一堆数据
4. LLM 看了看数据，说：数据太多了，我需要先筛选
5. 调用筛选工具
6. LLM 再看筛选后的数据，说：我需要画个图
7. 调用绘图工具
8. LLM 拿着图，生成分析报告
9. 返回给用户
```

这里有几个特点：
- **循环**：LLM 可能需要多次调用工具
- **分支**：根据 LLM 的判断，走不同的路径
- **不确定性**：你不知道 LLM 会调用几次工具，也不知道它会选择哪个工具

用 LangChain 的"链式调用"怎么写？很难。因为：
- 链是线性的，而 Agent 需要循环
- 链的步骤是固定的，而 Agent 的步骤是动态的

---

## LangChain 的解决方案：AgentExecutor

LangChain 最早提供了一个叫 `AgentExecutor` 的东西，专门用来运行 Agent：

```python
from langchain.agents import AgentExecutor, create_react_agent

agent = create_react_agent(llm, tools, prompt)
agent_executor = AgentExecutor(agent=agent, tools=tools)
result = agent_executor.invoke({"input": "北京天气"})
```

`AgentExecutor` 内部实现了一个循环：
1. 调用 LLM，看它想干什么
2. 如果 LLM 说要调用工具，就调用工具
3. 把工具的结果再喂给 LLM
4. 重复，直到 LLM 说"我有答案了"

这个方案能用，但有几个问题：

### 问题 1：不够灵活

`AgentExecutor` 把所有逻辑都封装在一个黑盒里。如果你想改一点点逻辑（比如"工具调用失败后，让 LLM 重试 3 次"），就得去改源码，或者继承 `AgentExecutor` 重写方法——非常麻烦。

### 问题 2：不支持复杂的多步骤流程

假设你想做一个这样的 Agent：
1. 先用 LLM 拆解任务
2. 把子任务分给不同的工具
3. 等所有工具都执行完
4. 再让 LLM 汇总结果

`AgentExecutor` 做不到——它只支持"LLM → 工具 → LLM"这种简单循环。

### 问题 3：状态管理混乱

在 `AgentExecutor` 里，状态（比如历史消息、工具调用记录）都是隐式管理的。你没法直接控制"在某个步骤保存一个中间结果"，也没法在多个 Agent 之间共享状态。

---

## LangGraph 的诞生：用图来表达 Agent 的工作流

LangChain 团队意识到，**Agent 的工作流本质上是一个"图"，而不是一个"链"**。

于是在 2024 年，他们推出了 LangGraph——一个用图结构来编排 Agent 的框架。

### LangGraph 的核心思想

1. **把 Agent 的每个步骤抽象成"节点"**  
   - 调用 LLM 是一个节点
   - 调用工具是一个节点
   - 判断逻辑是一个节点

2. **用"边"来连接节点，决定执行顺序**  
   - 固定的边：A 执行完就执行 B
   - 条件边：根据 A 的结果，决定执行 B 还是 C

3. **用"状态"在节点之间传递信息**  
   - 所有节点共享一个 State 对象
   - 节点可以读取和修改这个 State

4. **支持循环、分支、并行、暂停**  
   - 循环：节点 B 可以回到节点 A
   - 分支：根据条件选择下一个节点
   - 并行：多个节点同时执行
   - 暂停：在某个节点停下来，等人类输入

---

## 用 LangGraph 重写刚才的例子

还记得刚才的"分析销售数据"例子吗？用 LangGraph 可以这样表达：

```python
from langgraph.graph import StateGraph, MessagesState, START, END

# 定义节点
def call_llm(state):
    # 调用 LLM，判断下一步做什么
    ...

def query_database(state):
    # 查询数据库
    ...

def filter_data(state):
    # 筛选数据
    ...

def plot_chart(state):
    # 画图
    ...

# 构建图
graph = StateGraph(MessagesState)
graph.add_node("llm", call_llm)
graph.add_node("query_db", query_database)
graph.add_node("filter", filter_data)
graph.add_node("plot", plot_chart)

# 添加边
graph.add_edge(START, "llm")
graph.add_conditional_edges(
    "llm",
    should_continue,  # 判断：LLM 想做什么？
    {
        "query_db": "query_db",
        "filter": "filter",
        "plot": "plot",
        "end": END
    }
)
graph.add_edge("query_db", "llm")  # 查完数据库，回到 LLM
graph.add_edge("filter", "llm")    # 筛选完，回到 LLM
graph.add_edge("plot", "llm")      # 画完图，回到 LLM

app = graph.compile()
```

看到了吗？
- 每个步骤都是一个节点
- 用 `add_conditional_edges` 实现"根据 LLM 的判断，选择下一步"
- 用 `add_edge(节点A, 节点B)` 实现"执行完 A 就执行 B"
- 可以轻松实现循环（比如 `query_db → llm → query_db`）

---

## LangChain vs LangGraph：什么时候用哪个？

| 场景 | 用 LangChain | 用 LangGraph |
|------|-------------|-------------|
| 简单的问答 | ✅ | - |
| 固定的多步骤流程（如：检索 → 重排序 → 生成） | ✅ | - |
| Agent 需要动态选择工具 | - | ✅ |
| Agent 需要多次循环调用工具 | - | ✅ |
| 多个 Agent 协作 | - | ✅ |
| 需要人工审批某些步骤 | - | ✅ |
| 需要保存中间状态、支持暂停/恢复 | - | ✅ |

简单来说：
- **LangChain** 适合简单、固定的流程
- **LangGraph** 适合复杂、动态、需要循环和分支的 Agent

---

## 小结

LangChain 的"链式调用"适合线性流程，但 Agent 的工作流往往是非线性的——有循环、有分支、有不确定性。

LangGraph 用"图结构"来表达这种复杂的工作流，让你可以：
- 清晰地定义每个步骤（节点）
- 灵活地控制执行顺序（边）
- 方便地管理状态（State）
- 轻松地实现循环、分支、并行、暂停

从 LangChain 到 LangGraph，本质上是从"链式思维"到"图式思维"的转变。

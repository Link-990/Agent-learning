# 04-03 飞书 API、Webhook、事件订阅如何接入？

## 面试官追问

**面试官：** 做飞书 Agent 时，什么时候调用 API，什么时候使用 Webhook 或事件订阅？

**我：** API 用来读写数据，Webhook 用来接收消息，事件订阅用来监听变化。

**面试官：** 签名、去重、重试、顺序和权限如何设计？

## 常见错误回答

“收到事件后直接调用大模型处理，处理成功就返回 200。”

事件处理需要先快速确认、持久化和去重，再异步执行。否则模型延迟、重复投递或服务重启都会造成丢消息和重复操作。

## 30 秒简答

飞书 API 适合主动查询和执行读写操作，Webhook 适合向指定地址推送通知或接收外部回调，事件订阅适合监听消息、文档、审批等资源变化。接入时要完成应用身份、OAuth scope、请求验签、加密解密、事件去重、幂等、重试和死信处理。

事件入口只做鉴权、去重和入队，Agent 在异步消费者中处理；最终写操作使用幂等键，回调和 API 状态都要可观测。不要把事件顺序、一次投递或网络成功等同于业务成功。

## 原理拆解

### 1. 三种能力的职责不同

API 是请求-响应模型，由应用主动发起；Webhook 是 HTTP 推送通道，常用于通知和回调；事件订阅是平台按照事件类型推送变化，通常需要应用确认和异步消费。实际系统可以使用事件触发，再用 API 拉取完整资源。

### 2. 事件入口要快速返回

入口服务校验签名和 token，判断是否已处理，保存 event_id、tenant_key、发生时间和原始摘要，然后把任务放入队列并尽快返回。慢处理放到 worker，避免平台重试造成重复消费。

### 3. 一致性要通过幂等和对账保证

同一事件可能重复投递，事件顺序也可能与资源最终状态不一致。消费者用 event_id 或资源版本做去重，必要时再次调用 API 获取当前状态；定期对账弥补丢事件。

## 企业协作场景

审批状态变化事件到达后，服务先记录事件，再异步查询审批实例最新状态，更新任务系统并向用户发送卡片。即使事件重复到达，也不会重复创建任务或发送多条通知。

## 工程方案与取舍

1. 接入层和业务处理层分离，入口无状态、消费者可水平扩展。
2. 每类事件设置独立队列和重试策略，避免低优先级事件堵塞审批事件。
3. 保存验签失败、解析失败、业务失败和下游超时的分类指标。
4. 对关键资源建立事件与 API 对账任务，确认最终状态。

## 继续追问

**Q：Webhook 和事件订阅能互相替代吗？** 取决于平台能力和业务方向，Webhook 更偏通用回调，事件订阅更偏平台资源变化。

**Q：事件处理失败怎么办？** 分类重试，超过次数进入死信队列并支持人工重放，不能静默丢弃。

## 面试总结

飞书开放能力接入的关键不是会调用接口，而是建立可靠事件入口：验签、去重、入队、幂等、重试、对账和审计缺一不可。

## 深入展开：事件驱动系统的可靠性细节

### 1. 验签和解密要在业务逻辑之前

入口服务先校验请求来源、时间窗口、签名和加密字段，再解析事件类型。验证失败不应进入模型或业务队列，也不要在错误消息里返回内部验签细节。应用密钥和加密配置从安全存储读取，不能写死在代码或 Prompt 中。

### 2. 事件只说明“发生了变化”

很多事件并不携带完整资源，或者事件到达时资源已经再次变化。因此消费者通常使用事件中的资源 ID 调用飞书 API 获取最新状态，再以版本号或更新时间判断是否需要更新。事件正文不能直接作为最终事实。

### 3. 重试和死信要可观测

临时网络错误可以指数退避，参数错误和权限错误应进入人工可见的失败队列，连续失败的事件进入死信并保留原始摘要、错误码和重放次数。重放前要再次做权限和幂等检查，不能简单把消息重新推给 Agent。

### 4. 对账保证最终一致

对于文档、审批和任务等关键资源，定期拉取源系统的更新时间或版本列表，与本地状态对比。对账发现缺失时补发同步，发现本地多出时处理删除或失效。这样即使平台短暂丢事件，也不会永久造成数据漂移。

## API 和事件如何组成可靠链路

API 适合主动查询和执行，Webhook 适合被动接收外部通知，事件订阅适合把变化接入异步同步系统。三者不能互相替代：收到文档变更事件后，服务通常还要调用 API 拉取最新内容和权限；API 写入成功后，也要通过事件或对账确认源系统最终状态。事件本身只说明“某个资源发生变化”，不应直接当成完整业务事实。

事件入口要先验签、解密、去重并快速确认，再把事件写入可靠队列。消费者按 event_id 或资源版本幂等处理，失败进入延迟重试和死信队列。对于删除、权限收紧和审批状态变化等关键事件，需要定时对账，避免事件丢失、重复或乱序造成索引和源系统不一致。

飞书接口还要处理分页、限流、Token 过期、字段权限和局部成功。每次请求记录 request_id、租户、资源、接口版本和结果摘要；重试前判断操作是否安全，写操作必须带幂等键。面试时说明这些细节，才能证明你理解的是企业开放能力接入，而不只是调用一个 API 的 Demo。

## 面试追问补充：事件顺序和最终一致

同一资源的修改事件可能乱序到达，消费者不能只按到达时间覆盖索引，而要比较源版本、更新时间或事件序列。旧事件迟到时直接丢弃，但要保留丢弃原因；如果版本信息缺失，就重新向源系统拉取当前状态。对账任务发现差异后重新生成标准变更事件，避免每个消费者各自补偿。

Webhook 入口还要防重复投递和恶意重放。验签通过后记录 event_id 和时间窗口，重复事件只返回已处理状态；业务处理放到异步队列，避免在入口等待模型或大文件解析。故障恢复后按队列和对账结果补齐，而不是依赖服务重启自动“再跑一遍”。

## 面试追问补充：接口版本和兼容策略

飞书 API 字段和权限可能变化，连接器要记录 API 版本、scope、请求 ID 和响应摘要。对字段新增可以向后兼容，对字段删除或语义变化要通过适配层转换，并用契约测试验证分页、错误码、事件结构和幂等行为。升级前用真实回放样本检查，不要直接在所有租户全量切换。

不同租户的授权范围可能不同，能力清单要动态生成。工具找不到某个接口时，应返回明确的不可用原因，而不是让模型反复调用同一个不存在的能力。这样版本治理和运行时降级才能配合起来。

## 面试进阶回答

“API 是主动请求，Webhook 是回调通道，事件订阅是资源变化通知。我的入口层只负责验签、去重、持久化和快速确认，实际业务在异步 Worker 中完成；Worker 以源系统最新状态为准，配合幂等、重试、死信和定期对账保证可靠性。”

### 需要特别说明的边界

事件订阅解决“什么时候需要处理”，API 解决“如何取得完整数据或执行动作”。因此事件处理器不应该把事件内容直接当成最终答案，也不应该在入口请求里同步等待大模型完成。入口快速确认、队列可靠保存和 Worker 可重放，是比“能收到事件”更重要的生产能力。

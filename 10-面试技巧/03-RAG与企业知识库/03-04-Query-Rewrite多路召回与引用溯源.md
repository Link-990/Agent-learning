# 03-04 Query Rewrite、多路召回与引用溯源怎么设计？

## 面试官追问

**面试官：** 用户只问一句“这个怎么申请”，你如何让知识库找到正确答案？如果需要多份文档，引用怎么展示？

**我：** 先把问题改写得更完整，然后搜索相关文档。

**面试官：** 改写错了怎么办？多路召回结果冲突怎么办？模型生成的引用是真的吗？

## 常见错误回答

“让大模型把问题扩写成一段更长的文字，再用这段文字做向量搜索。”

Query Rewrite 如果没有保留原问题、用户身份和业务约束，可能把问题改错；引用如果只是模型生成一个链接，也不能证明答案真正来自该文档。

## 30 秒简答

我会保留原始 Query，同时根据意图、实体、时间、范围和同义词生成一个或多个检索 Query。不同 Query 走标题、关键词、向量、字段过滤等召回通道，再合并去重和排序。

回答阶段只允许引用实际进入上下文且通过权限过滤的证据，引用对象使用源文档 ID、块 ID、标题路径和版本，不让模型自由编造链接。遇到证据冲突，要展示版本和来源差异，不能静默拼接成一个结论。

## 原理拆解

### 1. 改写要结构化

可以让模型输出意图、实体、时间范围、关键词 Query、语义 Query 和过滤条件，例如：

```json
{
  "intent": "查询申请流程",
  "entities": ["出差"],
  "filters": {"status": "active"},
  "queries": ["出差申请流程", "差旅审批需要哪些材料"]
}
```

运行时要校验字段、限制改写长度，并在改写失败时回退到原始问题。

### 2. 多路召回要记录证据链

每条候选结果需要记录 query_id、retriever、score、rank、source_id、chunk_id 和过滤原因。这样可以回答“这段内容为什么被召回”，也方便比较不同检索器的贡献。

### 3. 引用溯源要从源数据生成

引用信息应由检索服务根据 source_id 和 chunk_id 生成，至少包含标题、章节、来源链接、版本和定位信息。模型只负责把引用放到答案相应句子后面，不能自行编造来源。

### 4. 冲突和无答案是正常分支

如果两个版本规则不一致，应优先依据有效期、发布状态和权威级别排序，并在答案中说明冲突。如果没有足够证据，系统应明确回答“当前知识库没有找到依据”，而不是用常识补全。

## 企业协作场景

员工说“新员工电脑怎么申请？”系统可以识别对象是设备申请，生成“新员工 IT 设备申请流程”“入职电脑领取材料”等多个 Query，同时过滤已失效制度。回答中的每条要求都链接到制度章节或申请入口。

## 工程方案与取舍

1. 原始 Query 永远保留，改写只作为额外召回路径。
2. 对高风险领域启用规则词典和实体校验，禁止模型擅自改变时间和金额条件。
3. 引用服务与生成模型解耦，引用缺失时答案降级为带证据的摘要或要求澄清。
4. 记录改写前后 Query、各路召回结果和最终引用，支持线上回放。

## 继续追问

**Q：什么时候不应该改写？** 用户问题已经包含唯一编号、完整标题或精确过滤条件时，应优先保留原 Query。

**Q：引用越多越好吗？** 不是。引用要覆盖关键结论且与句子相关，堆很多无关链接会降低可信度。

## 面试总结

Query Rewrite 的价值是扩大可检索表达，不是替用户重新提问。多路召回负责覆盖，证据链负责可解释，引用必须由系统根据真实检索结果生成。

## 深入展开：改写、召回和引用的边界

### 1. 改写不是一次性生成长句

复杂问题可以拆成多个互补 Query。例如“研发部门新员工如何申请电脑，预算和审批人是谁”，可以拆成申请流程、设备标准、预算规则和审批路由四个查询。每个查询保留原问题中的主体、时间和租户范围，最后再由系统合并证据。

改写模型输出前要经过结构校验：查询长度不能无限增长，时间范围不能被模型擅自改成“最近”，专有名词要和企业词典对齐。若实体识别置信度不足，优先向用户追问，而不是用一个看似合理的词替换。

### 2. 多路召回结果如何合并

不同召回器的分数不在同一尺度，不能简单把分数相加。可以使用排名融合、分桶归一化或学习排序。合并前去除同一 source_id 和 chunk_id 的重复结果，保留每条证据来自哪些 Query 和哪些召回器，便于解释和调参。

对结果冲突，先按文档状态、版本、来源等级和有效期处理；仍然冲突时在答案中并列说明，而不是让模型根据语言风格猜哪一条是真的。

### 3. 引用要覆盖结论而非装饰

一个答案可能有多个事实句，每句话应关联支持它的 Chunk。引用服务可以为每个证据生成稳定的 citation_id，生成模型只输出引用占位符，最终由程序把占位符替换成标题、章节和链接。若模型引用了没有进入上下文的 ID，系统应删除该引用或阻止回复。

引用链接还要检查访问权限和版本状态。用户在生成后失去权限时，点击链接不应打开内容；文档被删除后，历史答案也不应继续展示可访问的失效来源。

### 4. 没有答案时的产品策略

无答案不等于系统失败。可以说明已经搜索了哪些范围、缺少什么字段，并提供“换一个关键词”“选择时间范围”或“联系知识负责人”的下一步。对高风险问题，宁可返回证据不足，也不能用通用常识补上金额、审批人或合规结论。

## 一个完整的引用生成例子

用户问“今年差旅标准相比去年改了什么”，系统可以先把问题拆成“差旅标准、今年版本、去年版本、差异比较”四个检索意图，分别搜索制度编号、有效日期和版本标签。召回阶段同时走标题关键词、正文向量和版本元数据过滤，得到两份授权文档后，再由比较模块提取交通、住宿、审批和报销限制等字段。最终回答的每一条变化都绑定到对应版本和章节，而不是只在文末放两个链接。

如果检索到的文档日期冲突，系统应展示冲突并说明采用的版本依据；如果只有今年版本而找不到去年版本，应回答“当前只能确认今年规则”，而不是推断变化。引用服务要检查引用片段是否真的支持结论，例如引用只说明“适用于出差”，就不能用来证明具体金额。引用不是装饰格式，而是答案与证据之间的可验证关系。

在工程上，Query Rewrite 结果要记录原问题、改写版本、过滤条件和各路召回数量。这样出现“改写后反而搜不到”时，可以判断是模型扩展了错误实体、删除了关键限定词，还是检索器本身没有对应索引。对简单问题可以跳过改写，减少延迟；对复杂问题才启用多路计划，避免所有请求都付出相同成本。

## 一分钟进阶回答

“我会保留原 Query，用结构化 Rewrite 生成意图、实体、时间和多个检索表达，再走关键词、向量、标题和字段过滤。多路结果记录来源和分数，经过 ACL、去重和 Rerank 后形成证据集。引用由检索服务根据真实 Chunk 生成，模型不能自由编造；改写失败、证据冲突和无答案都走显式分支。”

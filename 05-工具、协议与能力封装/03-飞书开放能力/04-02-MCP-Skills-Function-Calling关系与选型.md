# 04-02 MCP、Skills、Function Calling 的关系与选型

## 面试官追问

**面试官：** MCP、Skills 和 Function Calling 有什么区别？做飞书 Agent 时应该选哪个？

**我：** 它们都是让大模型调用工具的方式，选一个就可以。

**面试官：** 一个是协议，一个是能力封装，一个是模型交互接口，你能把边界说清楚吗？

## 常见错误回答

“用了 MCP 就不需要 Function Calling，Skills 只是另一种 Prompt。”

三者处在不同层次。混淆它们会导致工具发现、权限管理和部署边界设计错误。

## 30 秒简答

Function Calling 是模型与应用运行时之间表达结构化动作意图的调用机制；MCP 是一种标准化的上下文、工具和资源连接协议，用来让客户端以统一方式发现和调用外部能力；Skills 更像面向任务的能力封装，包含说明、流程、约束和工具组合。

飞书场景中，应用内部少量稳定工具可以直接用 Function Calling；需要接入多个外部系统或复用工具服务时可以使用 MCP；复杂的“整理会议并创建待办”这类任务适合封装成 Skill，内部仍可通过 Function Calling 或 MCP 执行。

## 原理拆解

### 1. 三者的抽象层不同

```text
Skill：面向任务的能力与流程封装
  -> MCP：跨客户端的工具、资源和上下文连接协议
      -> Function Calling：模型表达结构化调用意图
          -> Runtime：权限、校验、执行与审计
```

它们可以组合使用，不是互斥选项。

### 2. 选型看复用边界

如果工具只服务于一个后端，直接注册 Function Calling 最简单；如果多个 Agent、IDE 或服务需要共享同一套外部工具，MCP 可以降低接入成本；如果用户面对的是完整工作任务，Skill 可以把步骤、判断标准和停止条件组织起来。

### 3. 安全边界不因协议改变

无论通过何种方式发现工具，最终都要经过服务端鉴权、参数校验、租户隔离、风险确认和审计。MCP Server 不是天然可信，远程工具同样要做来源、版本和权限管理。

## 企业协作场景

企业内部可以把飞书文档查询、审批查询和多维表格分析做成 MCP 工具服务；再把“周报生成”封装成 Skill；Agent 最终通过 Function Calling 请求某个具体工具。这样复用与任务体验都能兼顾。

## 工程方案与取舍

1. 工具数量少、边界固定时优先原生 Function Calling。
2. 外部工具多且需要跨应用复用时引入 MCP，但要增加服务治理和版本管理。
3. Skill 不直接持有高权限，具体写操作仍落到受控工具。
4. 统一工具注册表，记录协议来源、版本、权限和风险等级。

## 继续追问

**Q：MCP 一定比直接 API 好吗？** 不一定，标准化带来复用，也会增加服务部署和安全治理成本。

**Q：Skill 能不能绕过工具权限？** 不能，Skill 只是能力编排，权限必须在运行时和服务端校验。

## 面试总结

回答时按层次区分：Function Calling 是动作表达，MCP 是能力连接协议，Skills 是任务能力封装。实际系统可以组合使用，选型取决于复用范围、部署边界和治理成本。

## 深入展开：组合使用时的运行边界

### 1. 一个完整任务可以跨三层

以“整理会议纪要并创建待办”为例，Skill 描述任务目标、步骤和完成标准；MCP 提供会议记录、文档和任务系统等外部能力；模型通过 Function Calling 请求某个具体工具。最终的权限、参数校验和执行仍由 Runtime 负责。

### 2. 工具发现也需要治理

MCP 或动态注册工具时，不能把所有工具无差别暴露给模型。客户端应按租户、用户、场景和风险筛选工具，记录工具来源、版本、Schema 变化和最近使用情况。工具下线或权限变化时，缓存的工具描述也要失效。

### 3. Skills 要可测试和可回放

Skill 不应只是几段自然语言说明，而要有输入条件、步骤、工具白名单、成功标准、失败分支和停止条件。可以为 Skill 建立固定任务集，比较它和手工 Workflow、单轮 Function Calling 的完成率、成本和人工接管率。

### 4. 如何选择

如果只有两个内部工具，直接 Function Calling 成本最低；如果多个产品都要访问同一套文档和任务服务，MCP 的标准化收益更明显；如果用户要的是完整结果而不是单个 API 调用，则使用 Skill 组织流程更自然。不要为了“看起来先进”而引入多层协议。

## 三层能力如何一起落地

可以把一次“查找制度并创建待办”的任务拆成三层：Function Calling 负责让模型产生结构化动作；MCP 负责把文档搜索、任务创建等能力按统一协议暴露出来；Skill 负责把目标、步骤、约束、示例和失败处理组织成可复用能力。模型并不是直接调用某个协议，而是在运行时提供的工具和 Skill 上下文中做选择。

治理时要分别管理三种版本。工具 Schema 变化可能影响参数校验，MCP 服务变化可能影响连接和权限，Skill 变化可能影响任务规划。发布时应记录三者的组合版本，历史 Trace 回放也要固定这三个版本。工具发现不能把所有能力一次性暴露给模型，应按场景、租户和风险等级筛选，减少误选和提示注入面。

选型时还要看团队实际边界：单一应用、工具少且内部维护时，直接 Function Calling 足够；多个 Agent 或客户端要复用同一套工具时，MCP 的协议价值更明显；任务步骤、检查清单和人机协同较复杂时，才需要 Skill 层。三者可以组合，但每一层都要有清晰责任，不能把安全和业务规则藏进模糊的长 Prompt。

## 面试追问补充：复用能力也要可控

当多个 Agent 共用 MCP 工具时，服务端要为每个租户、用户和场景生成允许工具清单，不要把整个工具市场暴露给所有请求。工具的描述、示例和返回值也属于不可信输入，发现工具元数据被篡改时要能撤销版本并停止调用。

Skill 可以把复杂任务的前置条件、步骤、验收标准和人工节点固化下来，但不应把真实权限写死在文档里。权限、额度、资源版本和最终写入仍由运行时判断。这样既能复用经验，也能保证 Skill 失效或过期时不会绕开安全边界。

## 面试进阶回答

“我把三者看成不同层次的组合：Skill 面向任务，MCP 面向能力连接，Function Calling 面向模型动作表达。它们都不是权限边界，最终要回到统一 Runtime 做身份、Schema、风险、审计和版本控制。”

### 选择时再看两个问题

第一，工具是否需要被多个客户端复用；第二，能力是单个动作还是完整任务。前者决定是否引入 MCP，后者决定是否封装 Skill。无论选择哪种方式，都应保留直接禁用工具、锁定版本和回滚配置的能力。

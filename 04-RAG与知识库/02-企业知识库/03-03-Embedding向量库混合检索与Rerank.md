# 03-03 Embedding、向量库、混合检索与 Rerank 如何选型？

## 面试官追问

**面试官：** 你会怎么设计企业知识库的检索链路？只使用向量检索够不够？

**我：** 我会把文档做 Embedding 存到向量数据库，然后取相似度最高的几段。

**面试官：** 关键词、编号、日期和权限过滤怎么办？向量相似度最高就一定是最相关吗？

## 常见错误回答

“选一个更大的 Embedding 模型，再把 TopK 调大，效果自然会好。”

Embedding 解决的是语义表示，不解决全部检索问题。企业文档中有大量专有名词、编号、版本号和精确条件，单一向量检索容易漏召回或混入相似但错误的内容。

## 30 秒简答

我会使用混合检索：向量检索负责语义相似，BM25 或倒排检索负责关键词、编号和精确匹配，元数据过滤负责时间、文档类型和权限边界，多路召回后使用 Rerank 模型对候选结果重新排序。

Embedding 模型要结合语言、领域和成本评测，向量库需要支持索引更新、过滤、分片和备份。Rerank 只处理有限候选集，不能替代召回。最终以真实问题上的 Recall@K、MRR、NDCG、引用准确率、延迟和成本综合判断。

## 原理拆解

### 1. 召回和排序是两个问题

召回阶段追求“不要漏掉可能相关的内容”，可以并行调用向量、关键词、标题和元数据索引。排序阶段追求“把最能回答问题的内容排在前面”，可以使用加权融合、Reciprocal Rank Fusion 或 Rerank 模型。

```text
Query
-> 向量召回 / 关键词召回 / 标题召回
-> 合并去重
-> 权限与元数据过滤
-> Rerank
-> 邻接扩展与上下文压缩
```

### 2. Embedding 选型要看业务数据

评测集要覆盖中文表达、缩写、产品名、编号、跨句推理和多语言内容。除了命中率，还要关注向量维度、写入速度、查询延迟、模型调用成本和数据是否需要出域。模型升级时要支持双写和灰度，避免新旧向量不可比较。

### 3. Rerank 不能绕过权限

候选集进入 Rerank 前就应完成租户和 ACL 过滤，不能先把用户无权访问的文本交给第三方模型再过滤。Rerank 的输入应包含问题和候选 Chunk，输出相关性分数与排序，最终仍要结合来源质量、时效性和文档状态。

## 企业协作场景

用户问“2025Q4-PRD-017 的验收标准是什么？”关键词检索可以精准命中编号，向量检索可以补充“验收条件”同义表达，Rerank 再优先选择当前版本的产品文档，而不是旧版会议纪要。

## 工程方案与取舍

1. 先用向量加 BM25 建立基线，再根据失败样本引入标题召回和 Rerank。
2. 对短问题、编号问题和长问题采用不同的召回权重。
3. 对重复 Chunk、旧版本和低质量 OCR 内容做去重、降权或过滤。
4. 将检索耗时拆成各阶段指标，分别优化，而不是只看端到端平均延迟。

## 继续追问

**Q：向量数据库和普通数据库有什么区别？** 向量库擅长近邻搜索，但权限、事务和事实查询仍应依赖关系型或源系统。

**Q：为什么不能只用 Rerank？** Rerank 需要候选集，召回阶段漏掉的文档无法被它找回来。

## 面试总结

成熟的 RAG 检索不是“向量库加 TopK”，而是召回、过滤、排序、扩展和评测的组合。向量负责语义，倒排负责精确，Rerank 负责候选排序，权限和来源始终在模型之外控制。

## 深入展开：如何定位检索效果问题

### 1. 先判断是漏召回还是错排序

如果正确文档没有出现在候选集合里，这是召回问题，需要调整 Query、Embedding、关键词索引或过滤条件；如果正确文档已经在候选里但排名很低，这是排序问题，需要调整融合权重、Rerank 或来源质量降权。两类问题的修复方向完全不同。

我会在 Trace 中保存每个检索器的候选、分数和排名，并对同一个问题做离线回放。这样可以知道一个文档是被向量召回、关键词召回，还是只在标题召回中出现，而不是只看最后的 TopK。

### 2. 处理专有名词、数字和版本

企业检索中经常出现项目编号、缩写、产品代号和版本号。向量模型可能认为两个相似编号语义接近，但业务上完全不同。因此对编号、邮箱、日期和金额要做结构化识别，必要时采用精确过滤或关键词强约束。

版本管理也会影响排序。当前生效的制度应该优先于历史版本，官方发布的规则应该优先于个人会议纪要，但旧资料不能简单删除，因为它可能仍用于历史复盘。可以把有效期、来源等级和状态作为排序特征。

### 3. Rerank 的成本边界

Rerank 通常比一次向量查询更昂贵，因此不应把几百个候选全部交给它。先用廉价召回取出有限候选，再做权限过滤、去重和截断，最后用 Rerank 精排。对短问题或明确编号问题，可以跳过 Rerank；对长问题和多条件问题，再启用更强排序。

### 4. 评测和上线策略

至少建立三类样本：语义同义表达、精确编号查询和跨文档综合问题。对每类样本分别看 Recall@K、MRR、NDCG、引用正确率和端到端答案质量。模型或索引升级时做双写或离线重建，确认新旧索引的差异后再切换，不要直接覆盖生产向量。

## 进一步理解：如何把检索链路拆成可优化模块

如果召回不到答案，先不要马上换 Embedding 模型。可以固定问题和数据版本，分别查看关键词召回、向量召回、父块扩展和 Rerank 的候选集合。如果正确 Chunk 从未出现，问题在查询表达、索引字段或召回策略；如果正确 Chunk 出现但排名靠后，问题在融合权重或 Rerank；如果正确 Chunk 排名靠前但答案仍错，问题可能在上下文拼接、引用选择或生成约束。这个拆分能避免把所有错误都归因给模型。

混合检索还要考虑业务字段。标题、制度编号、项目代号、人员姓名和日期通常适合关键词或结构化过滤，概念相似和自然语言描述更适合向量召回。可以先用硬过滤缩小租户、空间、文档类型和有效期，再在授权范围内做多路召回。Rerank 的输入应包含标题、正文摘要、来源类型和版本信息，但不能使用被权限过滤掉的候选作比较。

线上优化时建议保留候选集和最终引用。每次改变 Embedding、索引参数或融合规则，都用同一批问题回放，比较 Recall@K、MRR、引用覆盖、无答案拒答率、P95 延迟和成本。某个模型在离线集上提升，如果线上长尾或权限场景变差，就不能直接全量发布。检索系统的质量来自数据、策略和评测共同作用，而不是单一模型名称。

## 常见追问延伸

**Q：为什么不把 TopK 调到很大？** 候选越多，噪声和上下文成本越高，模型还可能被相似但不相关的内容干扰。

**Q：Rerank 分数能跨模型比较吗？** 通常不能，应在同一模型和同一评测集内使用；跨模型要重新校准阈值。

**Q：向量库不可用怎么办？** 可以降级到关键词索引、缓存结果或明确提示检索暂不可用，但不能假装回答来自知识库。

# 4.5 与 StateGraph API 的对比与选择

学完了 Functional API 和 StateGraph API，现在我们来对比这两种方式，帮助你在实际项目中做出正确的选择。

---

## 同一个需求：两种实现

### 需求

构建一个简单的 Agent：
1. 调用 LLM
2. 如果 LLM 需要工具，调用工具
3. 把工具结果返回给 LLM
4. 重复直到 LLM 不再需要工具

### StateGraph API 实现

```python
from langgraph.graph import StateGraph, MessagesState, START, END
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")

def call_llm(state: MessagesState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

def call_tools(state: MessagesState):
    # 执行工具调用
    return {"messages": [tool_result]}

def should_continue(state: MessagesState):
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return "end"

# 构建图
graph = StateGraph(MessagesState)
graph.add_node("llm", call_llm)
graph.add_node("tools", call_tools)

graph.add_edge(START, "llm")
graph.add_conditional_edges("llm", should_continue, {
    "tools": "tools",
    "end": END
})
graph.add_edge("tools", "llm")

app = graph.compile()
```

**代码行数：约 25 行**

### Functional API 实现

```python
from langgraph.func import entrypoint, task
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")

@task
def call_llm(messages: list):
    return llm.invoke(messages)

@task
def call_tools(tool_calls):
    # 执行工具调用
    return tool_result

@entrypoint
def agent(messages: list):
    while True:
        response = call_llm(messages)
        
        if not response.tool_calls:
            return response
        
        tool_result = call_tools(response.tool_calls)
        messages.append(response)
        messages.append(tool_result)
```

**代码行数：约 15 行**

## 详细对比

### 1. 代码风格

| StateGraph API | Functional API |
|----------------|----------------|
| 显式定义图、节点、边 | 用普通函数 + 装饰器 |
| "声明式" | "命令式" |
| 看代码知道图的结构 | 图结构是编译出来的 |

**StateGraph**：适合"先设计图，再实现节点"的思维方式

**Functional**：适合"直接写逻辑，让 LangGraph 去编译"的思维方式

---

### 2. 灵活性

| 场景 | StateGraph | Functional |
|------|-----------|-----------|
| 简单线性流程 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 简单分支（if-else） | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 复杂循环（动态路由） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 动态并行 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 需要可视化图结构 | ⭐⭐⭐⭐⭐ | ⭐⭐ |

**StateGraph 更灵活**，可以表达任意的图结构。

**Functional API 受限于 Python 的控制流**，不适合"动态决定有几条分支"这种场景。

---

### 3. 学习曲线

| 阶段 | StateGraph | Functional |
|------|-----------|-----------|
| 入门 | 需要理解"图"的概念 | 就是写普通函数 |
| 进阶 | 理解节点、边、路由 | 理解 task、可注入参数 |
| 高级 | 理解 checkpointer、interrupt | 同样需要理解这些 |

**Functional API 入门更快**，但高级特性（checkpointer、interrupt）的理解成本是一样的。

---

### 4. 可读性

#### StateGraph：图结构清晰

```python
graph.add_edge(START, "llm")
graph.add_conditional_edges("llm", router, {"tools": "tools", "end": END})
graph.add_edge("tools", "llm")
```

一眼看出：`START → llm → 判断 → tools/END`

#### Functional：逻辑流程清晰

```python
while True:
    response = call_llm(messages)
    if not response.tool_calls:
        return response
    tool_result = call_tools(response.tool_calls)
    messages.append(tool_result)
```

一眼看出：循环调用 LLM 和工具，直到不需要工具。

**结论**：各有优势，取决于你想强调"图结构"还是"逻辑流程"。

---

### 5. 调试体验

#### StateGraph

```python
for event in app.stream(input):
    print(f"节点: {list(event.keys())[0]}")
    print(f"输出: {event}")
```

可以清楚地看到每个节点的执行顺序和输出。

#### Functional

```python
for event in workflow.stream(input):
    print(event)
```

task 的执行会被追踪，但节点名可能不如 StateGraph 直观。

**StateGraph 的调试体验稍好**，因为节点名是你显式定义的。

---

### 6. 性能

**两者性能基本一致**——Functional API 最终也会编译成图。

唯一的区别：Functional API 有一次编译开销（第一次调用时）。

---

### 7. 团队协作

| 场景 | StateGraph | Functional |
|------|-----------|-----------|
| 团队有图论背景 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 团队习惯函数式编程 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 需要给 PM 展示流程图 | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| 快速原型开发 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

## 何时选择 StateGraph？

### 场景 1：复杂的路由逻辑

```python
# 根据 LLM 输出，动态决定调用哪个工具
def route_tools(state):
    tool_name = state["messages"][-1].tool_calls[0]["name"]
    return tool_name

graph.add_conditional_edges(
    "llm",
    route_tools,
    {
        "search": "search_tool",
        "calculator": "calculator_tool",
        "database": "database_tool",
        "end": END
    }
)
```

这种"一对多"的动态路由，StateGraph 表达起来很自然。

### 场景 2：需要可视化

如果你要把 Agent 的流程图画出来（给团队看、给客户看），StateGraph 的结构更清晰。

### 场景 3：团队已经熟悉 StateGraph

如果团队已经有 StateGraph 的代码库，保持一致性。

---

## 何时选择 Functional API？

### 场景 1：简单的线性流程

```python
@entrypoint
def workflow(topic: str) -> str:
    outline = generate_outline(topic)
    essay = write_essay(outline)
    final = polish(essay)
    return final
```

这种直线型的流程，Functional API 更简洁。

### 场景 2：快速原型

想快速验证一个想法，不想花时间设计图结构：

```python
@entrypoint
def prototype(input: str) -> str:
    # 快速写逻辑
    result = step1(input)
    if result.needs_more:
        result = step2(result)
    return result
```

### 场景 3：团队习惯函数式编程

如果团队成员都习惯写纯函数、链式调用，Functional API 更自然。

---

## 混合使用？

**可以！** 在同一个项目里，可以同时使用两种 API：

```python
# 简单的子流程用 Functional API
@entrypoint
def simple_workflow(input):
    return process(input)

# 复杂的主流程用 StateGraph
graph = StateGraph(State)
graph.add_node("simple", simple_workflow)  # 把 Functional 当作节点
graph.add_node("complex", complex_node)
```

---

## 迁移建议

### 从 StateGraph 迁移到 Functional

如果你的工作流很简单（线性或简单分支），可以考虑迁移：

**迁移前（StateGraph）**：

```python
graph = StateGraph(State)
graph.add_node("step1", step1)
graph.add_node("step2", step2)
graph.add_edge(START, "step1")
graph.add_edge("step1", "step2")
graph.add_edge("step2", END)
app = graph.compile()
```

**迁移后（Functional）**：

```python
@entrypoint
def workflow(input):
    result1 = step1(input)
    result2 = step2(result1)
    return result2
```

### 从 Functional 迁移到 StateGraph

如果你的工作流变复杂了（需要动态路由、复杂循环），可以迁移到 StateGraph。

## 实战决策树

```
你的 Agent 工作流是什么样的？
├─ 线性流程（A → B → C）
│  └─ 选择 Functional API
├─ 简单分支（if-else）
│  └─ 选择 Functional API
├─ 简单循环（while 循环）
│  └─ 选择 Functional API
├─ 需要动态路由（根据 LLM 输出决定下一步）
│  └─ 选择 StateGraph API
├─ 需要可视化流程图
│  └─ 选择 StateGraph API
└─ 不确定会不会变复杂
   └─ 选择 StateGraph API（更灵活）
```

---

## 小结

| 维度 | StateGraph API | Functional API |
|------|----------------|----------------|
| 代码风格 | 声明式，显式定义图 | 命令式，写普通函数 |
| 学习曲线 | 需要理解图的概念 | 更直观 |
| 灵活性 | 非常灵活 | 受限于 Python 控制流 |
| 适合场景 | 复杂工作流、动态路由 | 简单到中等复杂度 |
| 可视化 | 容易 | 较难 |
| 代码量 | 较多 | 较少 |

**推荐策略**：
- 刚开始学 LangGraph → 先学 StateGraph，打好基础
- 快速原型 → Functional API
- 生产环境、复杂 Agent → StateGraph API
- 简单工具链 → Functional API

两种 API 各有优势，选择适合你的场景即可。很多情况下，它们可以混合使用。

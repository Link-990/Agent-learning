# 03-01 飞书文档、知识库、云盘、多维表格如何接入？

## 面试官追问

**面试官：** 如果要做一个飞书企业知识问答 Agent，你会怎么接入文档、知识库、云盘和多维表格？是把所有内容统一导入向量库吗？

**我：** 我会把它们都转成文本，然后做 Embedding 存进向量数据库。

**面试官：** 文档和多维表格是同一种数据吗？用户能看到的数据你都能读取吗？权限变化和删除怎么处理？

这道题考察的是数据源建模、同步边界和权限意识，而不是会不会说“接入 RAG”。

## 常见错误回答

“所有数据都定时同步到一个向量库，查询时直接召回最相似的内容。”

这个方案忽略了数据类型、访问权限、实时性和原始来源。向量库适合做检索索引，但不应该成为企业数据的唯一事实来源。

## 30 秒简答

我会把飞书文档、知识库节点、云盘文件和多维表格看成不同类型的数据源，先通过统一连接器获取元数据、正文、结构化字段和权限信息，再按数据类型采用不同解析策略。文档和 PDF 进入解析与分块链路，多维表格保留表、字段、视图和记录结构，必要时通过实时查询获得最新值。

索引中必须保留 source_type、source_id、parent_id、更新时间、版本和 ACL 摘要，检索时先做权限过滤，回答时回链到原文档或表格。同步链路要支持首次全量、增量更新、删除和失败重试，向量库只做可重建的检索加速层。

## 原理拆解

### 1. 不同数据源要保留原生语义

飞书文档通常是层级化富文本，知识库节点同时包含空间和父子关系，云盘文件可能是 PDF、表格、图片或压缩包，多维表格则包含字段类型、视图、记录和公式。统一转成纯文本会损失标题层级、表头、字段类型和来源关系。

因此索引对象至少分为 document、file、bitable、table、record、wiki_node 等类型，并把原始 token、父节点和版本号保留下来。

### 2. 接入层与检索层分离

连接器负责鉴权、分页、增量游标和限流，解析器负责把源数据转成统一的中间表示，索引器负责生成 Chunk、Embedding 和倒排字段，回答层负责权限过滤、引用和回链。任何一层都不能假设向量库是最终事实。

```text
飞书 API / 事件
-> 连接器与同步游标
-> 统一内容模型
-> 解析、切分、元数据
-> 向量索引 + 关键词索引
-> ACL 过滤
-> 带来源回答
```

### 3. 多维表格不能只按段落切分

对多维表格，除了把记录转成可检索文本，还要保存字段名、字段类型、表名、视图、记录 ID 和更新时间。涉及“本月销售额”“状态为进行中”等问题时，Agent 应优先生成受控查询计划，再由表格查询工具实时计算，避免依赖过期的文本 Chunk。

## 企业协作场景

员工问：“华东区域本周延期项目有哪些，负责人和风险原因是什么？”系统可以先从知识库检索项目规范和风险定义，再查询多维表格中的最新记录，最后回到项目文档补充原因。三类数据分别承担规则、事实和解释，不能简单混成一类文本。

## 工程方案与取舍

1. 文档类数据采用事件触发加定时校准，表格类数据对关键指标保留实时查询路径。
2. 为每个连接器设置独立的游标、限流、重试和死信队列，避免一个数据源故障拖垮全量同步。
3. 保存原始快照或可重放的变更日志，索引异常时可以重建，不依赖人工补数据。
4. 先实现只读检索和引用，再逐步增加表格写入、任务创建等操作。

## 继续追问

**Q：为什么不把所有内容复制到一个数据库？** 复制可以提高检索效率，但会带来同步延迟、权限漂移和删除不一致，原系统仍应是事实源。

**Q：怎样判断同步完成？** 需要按数据源记录游标、成功数、失败数、删除数和最后校准时间，而不是只看任务是否返回成功。

## 面试总结

回答时先区分数据源，再说明连接器、统一内容模型、索引、权限和实时查询的边界。核心原则是：统一检索体验，不等于抹平数据类型；向量索引可重建，原始系统负责事实和权限。

## 深入展开：如何把接入方案做成可上线能力

### 1. 先建立统一资源模型

接入不同飞书资源时，我不会直接把所有内容塞进一个 `content` 字段，而是先定义统一资源模型：`tenant_id` 表示租户，`source_type` 表示文档、云盘文件、知识库节点或多维表格，`source_id` 表示原始资源，`parent_id` 表示层级关系，`version` 和 `content_hash` 表示当前版本。正文、结构化字段、来源链接、更新时间和 ACL 摘要分开存储。

这样做的好处是后续可以按资源类型路由解析器，也可以在某个数据源出现问题时只重建对应分区。例如 PDF 解析器升级，不需要重新处理所有飞书文档；多维表格字段变化，也不应该影响文档索引。

### 2. 全量、增量和实时查询要分工

首次接入通常需要全量扫描，建立资源清单和初始索引；日常变化使用事件订阅、更新时间窗口或变更游标做增量同步；对金额、库存、任务状态等强实时字段，直接通过受控工具查询源系统。三种方式不是互斥的，而是分别解决初始化、低延迟更新和事实准确性。

同步任务要把“发现变化”和“处理变化”分开。发现层只负责记录新增、修改、删除事件，处理层再异步解析和索引。如果处理失败，可以从事件表重放；如果事件丢失，定期校准任务可以对比源系统清单和索引清单。

### 3. 一个完整的排障例子

如果员工说“明明有这份制度，为什么搜不到”，我会按以下顺序排查：第一，资源是否被连接器发现；第二，是否因为权限过滤而不可见；第三，解析器是否提取为空；第四，Chunk 是否被错误切分；第五，Embedding 或关键词索引是否写入成功；第六，Query Rewrite 和 Rerank 是否把结果降权；第七，答案生成是否因为证据不足而拒答。

每一步都要有状态和指标，而不是重新运行一次同步任务碰运气。只有把链路拆开，才能判断是数据接入问题、检索问题还是权限问题。

### 4. 面试中的进阶回答

如果数据量较小，我会优先做稳定的连接器和统一资源模型，不急着建设复杂的多 Agent。等只读问答验证价值后，再针对多维表格增加实时分析工具，针对云盘文件增加 OCR 和附件解析，针对知识库增加父子节点和空间级 ACL。这样可以让架构随着真实问题演进，而不是一开始就把所有数据源做成一个难以维护的“大一统 RAG”。

## 接入方案中的进一步追问

面试官还可能问：“如果同一份内容同时出现在知识库和云盘，如何避免重复？”我会给资源建立规范化主键和来源关系，先判断是否是同一个源文件、同一版本或同一份快捷方式，再决定合并索引还是分别保留。合并时不能只去重正文，还要保留多个可访问的回链和各自的 ACL；如果权限范围不同，就必须按用户权限分别过滤，不能因为内容相同就把权限较宽的版本暴露给所有人。

另一个问题是“连接器拿不到全部字段怎么办”。这时要把资源状态标成部分可用，保存已获取的元数据和失败原因，回答中明确说明数据可能不完整。对于多维表格，字段定义、视图条件和公式依赖尤其重要，不能只同步展示出来的几列；对于文档，附件、评论和历史版本也要明确是否纳入范围。把接入边界写出来，后续的检索结果才有可信的解释。

## 上线检查清单

- 是否记录每个数据源的游标、版本、失败数和最后校准时间？
- 文档删除、撤回和权限变化是否能让检索与缓存失效？
- 多维表格的字段类型、视图和统计口径是否保留？
- 查询结果能否回到原文档、表格视图或具体记录？
- 任意同步失败是否可以重试、重放或人工接管？

# 03-06 ACL 权限过滤与越权防护

## 面试官追问

**面试官：** 企业知识库怎样保证用户只能看到自己有权限访问的内容？把权限信息存进 Chunk 就够了吗？

**我：** 可以在文档同步时把部门信息存到元数据里，检索时按部门过滤。

**面试官：** 用户可能同时属于多个群组，文档权限会变化，模型会不会从其他文档推断出机密内容？

## 常见错误回答

“在 Prompt 里告诉模型不要回答没有权限的内容。”

Prompt 不是权限边界。真正的访问控制必须发生在检索、工具调用和结果拼接之前，模型只能看到已经授权的数据。

## 30 秒简答

我会把用户身份、租户、部门、群组、资源 ACL 和操作权限统一建模。检索前由授权服务生成当前用户的有效权限上下文，在候选召回阶段做硬过滤；即使使用缓存、Rerank 或父块扩展，也要再次校验。

回答中只使用通过 ACL 的证据，引用链接也要经过权限检查。权限变化采用短时缓存和事件失效，高风险数据不跨租户索引。对于无法确认权限的内容，默认拒绝并返回可解释提示，而不是让模型猜测。

## 原理拆解

### 1. 认证和授权不是一回事

认证回答“你是谁”，授权回答“你能访问什么、能做什么”。用户登录态、租户和身份来源由认证系统提供，资源访问则由 ACL、RBAC、ABAC 或源系统权限决定。检索服务不应仅凭用户姓名或部门字符串授权。

### 2. 权限过滤要尽量前置

最佳路径是把 tenant_id、space_id、resource_id、principal_id 和 allow/deny 条件转成检索过滤器，在候选进入模型前完成过滤。父子 Chunk、相邻块、摘要缓存和引用生成都要继承同一权限约束。

### 3. 处理权限变化和缓存

权限缓存必须有 TTL、版本或事件失效机制。资源权限变更时，至少让检索索引中的 ACL 摘要和答案缓存失效。高敏感资源可以采用实时鉴权，不依赖长时间缓存。

### 4. 防止间接泄露

即使模型没有直接引用机密文档，也可能通过统计、摘要或“是否存在某项目”间接泄露信息。因此要限制跨权限聚合、错误提示和搜索结果数量，对敏感意图触发更严格的确认或人工审批。

## 企业协作场景

员工询问“某客户的报价底价是多少”。系统先判断员工是否属于对应项目和客户权限范围，未授权时不返回文档标题、金额区间或“存在该文件”的提示；有权限时才从有效版本中生成带来源答案。

## 工程方案与取舍

1. 租户隔离放在索引分区或强制过滤层，不能只靠业务代码约定。
2. 高敏感数据采用源系统实时鉴权，普通知识可以使用短时 ACL 缓存。
3. 记录每次检索的用户、权限版本、过滤结果和引用，便于审计。
4. 对越权测试使用反向问题、跨部门账号和权限变更后的缓存场景。

## 继续追问

**Q：能不能把所有权限都写进 Prompt？** 不能，Prompt 可被注入，也无法替代源系统的实时权限判断。

**Q：权限过滤放在 Rerank 后可以吗？** 不可以，未授权数据不应进入模型或第三方 Rerank。

## 面试总结

ACL 防护的底线是“未授权数据不进入模型上下文”。认证、授权、检索过滤、缓存失效、引用校验和审计必须形成闭环。

## 深入展开：权限模型如何落到检索实现

### 1. 先明确主体、资源和动作

主体可以是用户、部门、群组、应用或服务账号，资源可以是文档、知识库节点、文件、表格、视图和记录，动作至少区分 read、comment、edit、share、delete 和 export。只记录“部门=研发”是不够的，因为同一部门内还可能存在项目级 ACL 和临时授权。

### 2. ACL 过滤的两种实现

一种方式是在索引元数据中写入可访问主体或权限标签，检索时做硬过滤；另一种方式是先召回候选，再向源系统或授权服务批量校验。前者性能好但权限变化需要快速同步，后者实时性强但延迟更高。高敏感资源可以组合使用：索引先粗过滤，最终引用前再实时确认。

### 3. 缓存、父块和聚合是高风险点

即使主 Chunk 通过权限过滤，父块、邻接块、摘要缓存和历史答案也可能带出无权内容。所有扩展都要携带原始 resource_id 并再次检查；聚合回答不能把多个用户可见范围混为公共缓存。缓存键至少绑定 tenant_id、principal_id 或权限版本、query_hash 和数据版本。

### 4. 越权测试不能只测“搜不到”

要测试文档标题是否泄露、搜索结果数量是否泄露、模型是否能从公开摘要推断机密、权限撤销后缓存是否仍可访问，以及通过工具参数改写资源 ID 是否越权。还要使用同名用户、跨租户账号、临时群组和管理员账号进行对照。

## 权限过滤的测试和审计方法

权限测试不能只创建一个“有权限用户”和一个“无权限用户”，还要覆盖继承权限、临时授权、离职回收、跨部门共享、快捷方式、父子文档和缓存命中等情况。可以为同一资源建立用户、部门、群组和租户四类主体，分别测试读取、搜索、引用、下载和写入动作。任何一个动作越权，都应按安全事件处理，而不是只当成普通答案错误。

检索前过滤和检索后过滤各有适用场景。前置过滤能减少候选暴露和排序干扰，但依赖索引中 ACL 足够新；后置过滤可以作为第二道防线，但不能让模型先看到未授权内容。生产系统通常两者都做，并在 Trace 中记录权限快照、过滤前后候选数量和拒绝原因，方便解释“为什么搜不到”以及发现权限漂移。

缓存必须绑定租户、主体、资源版本和权限版本。一个管理员命中的答案不能直接复用给普通员工；权限收紧后，相关缓存要通过事件或版本号快速失效。引用、摘要和统计结果同样可能泄露信息，因此不能只保护原文下载接口。面试时强调“权限是每次请求的运行时约束”，比只说“数据库有 ACL 字段”更完整。

## 权限问题的产品化处理

用户问“为什么搜不到”时，不能透露隐藏资源的名称，但可以给出安全的解释：当前账号没有访问权限、资源正在同步、资料已过期，或系统暂时无法确认权限。必要时提供申请访问、联系管理员或查看公开版本的入口。这样既保护资源存在性，也避免用户把权限问题误判为系统没有数据。

权限变化要和事件、缓存、索引、引用和异步任务联动。用户失去权限后，正在生成的答案应在最终发送前重新检查；已经生成但未发送的卡片不能继续执行导出；被删除资源的 Trace 只能保留脱敏元数据。将权限作为每一步的运行时约束，才能覆盖聊天、搜索、下载和工具调用的所有出口。

## 面试最后补充

权限防护的验收不是“管理员能搜到、普通用户搜不到”这么简单，还要验证引用、摘要、下载、导出、缓存和异步任务都遵守同一套策略，并保留拒绝原因与版本。权限变化时宁可暂时拒答，也不能继续使用无法确认授权状态的旧证据。

## 一分钟进阶回答

“我会把认证和授权分开，授权判断绑定主体、租户、资源、动作和策略版本。检索前做租户和 ACL 硬过滤，父子块、缓存、Rerank 和引用阶段继续继承权限；权限事件让缓存和索引失效。工具调用和答案出口也要重新校验，审计记录权限决策。底线是未授权数据不进入模型上下文。”

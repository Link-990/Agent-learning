# 10.6 从 Kami Code 学到的最佳实践

通过深入分析 Kami Code 的 LangChain 使用方式，我们总结出以下最佳实践。

---

## 1. 协议适配 > 框架绑定

Kami Code 用 LangChain 的**协议标准**（StructuredTool、AgentMiddleware、usage_metadata），但不绑定 LangChain 的框架。

**最佳实践**：
- 用 LangChain 的工具协议让工具生态互通
- 用 try/except ImportError 做优雅降级
- 核心逻辑与 LangChain 解耦

---

## 2. 两层工具系统

Kami Code 的工具系统分两层：
- **内部层**（ToolSpec）：完整的工具规范，包含项目特有的元数据
- **适配层**（StructuredTool）：LangChain 标准接口，附加 metadata

**最佳实践**：
- 内部定义可以很丰富（source、risk_level、permission_scope...）
- 对外暴露标准接口（StructuredTool）
- 用 metadata 桥接两层

---

## 3. Middleware 做工具过滤

当工具很多时，不能全部暴露给 LLM。Kami Code 用 `DeferredToolMiddleware` 实现按需加载。

**最佳实践**：
- 标记工具的加载策略（`defer_loading`）
- 用 Middleware 在 LLM 调用前过滤
- 只暴露当前需要的工具，减少 Token 消耗

---

## 4. 多 Provider 兼容

Kami Code 的 Token 追踪同时支持 LangChain、OpenAI、Anthropic 三种格式。

**最佳实践**：
- 优先读 LangChain 标准格式
- 回退到 Provider 特有格式
- 做好兼容，不假设单一 Provider

---

## 5. Schema 验证

用 `convert_to_openai_tool` 验证工具 Schema 能被所有 Provider 解析。

**最佳实践**：
- 在测试中验证 Schema 转换
- 确保 `properties`、`required` 等字段正确
- 用 `strict=True` 做严格验证

---

## 总结：Kami Code 的设计哲学

| 原则 | 说明 |
|------|------|
| **协议优先** | 用标准协议，不被框架锁定 |
| **优雅降级** | try/except 保证兼容性 |
| **按需加载** | 工具不是越多越好 |
| **多 Provider** | 不假设单一 Provider |
| **Schema 验证** | 确保工具定义的互通性 |
